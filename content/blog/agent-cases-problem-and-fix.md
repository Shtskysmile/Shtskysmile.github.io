# 从「能跑」到「可靠」：三个 Agent 应用的问题定位与改进

> 准备 Agentic AI 岗笔试时做的一组练习题，要求手写、能讲清机制，核心命题是「用 Agentic AI 减少垂直领域 LLM 幻觉」。
>
> 三道具代表性的题：一道工具调用 + 循环（电商客服助手），一道 RAG（产品手册问答），一道带长期记忆的多轮助理（窗口管理与记忆）。下面按问题、分析、初版、改进的顺序，各走一遍。

## 一、三道题要解决什么

| | 客服助手 | 产品手册问答 | 带记忆的个人助理 |
| --- | --- | --- | --- |
| 形态 | 工具调用 + ReAct 循环 | RAG（检索 + 生成） | 多轮对话 + 长期记忆 |
| 症状 | 多步问题答一半、不存在的单号把程序带崩 | 答错、编造、没有出处 | 忘开头、结构报错、记忆用不上 |
| 考点 | 循环的退出条件、工具失败怎么兜底 | 检索对不对、引用能不能压住幻觉 | 裁剪的边界、记忆怎么进上下文 |

三道题看着差挺远，其实是同一件事。一个不可靠的 LLM 应用，坏就坏在模型不知道自己不知道——不知道工具刚失败了，不知道手上的资料够不够，也不知道开头说过的话还在不在。所以改法也一致：把边界做成模型看得见的东西。

## 二、客服助手（Agent 循环）

### 题目要求

做电商客服助手，工具三个：`get_order` 查订单、`get_refund_policy` 查退货政策、`list_orders_by_customer` 列客户订单。要求两条：

1. 只查一次的问题（"订单 A1001 的金额是多少"）基本能答对。但连着查好几步的（"客户 chen_wei 名下所有订单里，哪几件还在退货期内、各自退货扣多少手续费"），答案经常只覆盖一部分，甚至干脆是错的，还不报错，语气很肯定。
2. 问到不存在的订单号，程序直接抛异常退出。

### 先分析

- 「答一半却不报错」，说明循环的退出条件不可靠。它以为自己答完了，其实还在半路上。
- 「不存在的单号直接崩」，说明失败没被翻译成模型能理解的信息，而是变成了程序崩溃。

所以这题真正考的是两件事：循环什么时候算结束，工具失败时怎么办。方向也就是把这两件事，从"程序内部的状态"变成"模型能看到的观察"。

### 初版

我写的循环大概是这样：

```python
for i in range(max_step):
    resp = client.chat.completions.create(messages=messages, tools=TOOLS, model="deepseek-chat")
    if resp.choices[0].finish_reason == 'stop':
        break                     # 模型说完了，退出
    assistant_msg = resp.choices[0].message
    messages.append(assistant_msg.model_dump())
    for tc in assistant_msg.tool_calls:
        tc_result = TOOL_IMPL[tc.function.name](**json.loads(tc.function.arguments))
        messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(tc_result)})

return resp.choices[0].message.content
```

多步的问题确实答对了。问 chen_wei 那单，它能走完：查客户订单、逐个查订单、查类目政策、最后汇总。方向没错。

但两个要求各自都还差一口气。而这两口气，恰好就是上面说的那两件事。

### 坑一：崩在工具失败，我一开始却以为是循环的错

查一个不存在的单号，实测直接崩：

```
CRASHED: KeyError 'A9999'
```

我第一反应是加兜底，于是在循环后面补了一句：

```python
if resp.choices[0].finish_reason != 'stop':
    return "There is some err of getting result"
```

结果照样崩。

原因后来才想明白：异常是在循环内部 `get_order('A9999')` 那一行抛出来的。Python 一遇到没人管的异常就立刻往上弹，循环后面那句兜底根本轮不到执行。兜底没站在异常必经的路上。

这个循环其实有三个出口：模型收敛、步数耗尽、工具抛异常。我守了前两个，漏了第三个，而崩溃恰恰从第三个走。

### 坑二：退出信号选错了

我原本靠 `finish_reason == 'stop'` 判断"做完了"。但 finish_reason 说的是模型这一轮想干什么，取值还有 `length`（被截断）、`content_filter` 之类。模型明明答完了，却因为输出被截断成 length，就会被误判成没完，白跑一轮。

更可靠的信号是：这一轮有没有 `tool_calls`。模型不再要工具，就是准备用手上的信息说话了。这个信号跨厂商都成立。

顺带还发现一件事。如果循环走满 `max_step`，我返回的 `resp` 是最后一轮的，而它的 `content` 可能是句没写完的前言：

```python
# finish_reason == 'tool_calls' 那一轮，message.content 实测长这样
"I'll look up the details for order A1001."
```

也就是说，循环耗尽时我会把一句中间前言当成答案交给用户。不报错，语气还很肯定。题目里那句"答案只覆盖一部分、而且不报错"，有一半就是从这来的。

### 改进一：工具层，失败要"返回"，不要"抛出"

数据访问层不该把裸 KeyError 漏给上层，所以修在工具实现里：

```python
def get_order(order_id: str) -> dict:
    order = ORDERS.get(order_id)
    if order is None:
        return {"error": f"订单号 {order_id} 不存在，请确认后重试"}
    return order
```

重点不在于不崩，而在于这个结果是喂给模型的。带着 error 字段回到 `role: "tool"` 的消息里，模型读得懂，自己就会改口：

> 抱歉，订单号 A9999 不存在，我无法查询到它的金额。请确认订单号是否正确……

这是压幻觉里最直接的一招：把失败变成模型能推理的一条普通观察，而不是让程序替它决定"完蛋了"。很多幻觉就是因为模型根本不知道前提已经失败。

### 改进二：循环层，换退出信号，再加降级作答

```python
completed = False
for _ in range(max_step):
    resp = client.chat.completions.create(messages=messages, tools=TOOLS, model="deepseek-chat")
    assistant_msg = resp.choices[0].message

    if not assistant_msg.tool_calls:      # 没有工具调用 = 准备作答
        completed = True
        break
    # ... 执行工具、追加 tool 消息 ...

if completed:
    return assistant_msg.content

# 步数耗尽：不再给 tools，让模型基于已有信息降级作答
messages.append({
    "role": "user",
    "content": "工具调用次数已达上限，你无法再查询新信息。"
               "请仅根据上面已经获得的结果作答，并明确说明哪些部分尚未查到或无法确认。",
})
final = client.chat.completions.create(model="deepseek-chat", messages=messages)  # 不带 tools
return final.choices[0].message.content
```

我把 `max_step` 临时改成 1 强制触发过一次，它答成这样：

> 目前我仅查到客户 chen_wei 名下有 2 笔订单：A1001 和 A1002。但由于工具调用次数已达上限，我无法继续查询……所以关于"哪几件还在退货期内"，我目前无法确认，无法给出答案。

这就是 agent 在最坏情况下该有的样子：给出已经确认的那点事实，再讲清楚缺了什么。比一句没有信息量的报错强，更比硬编一个答案强。用户至少知道有 2 笔订单、详情没查到，也就知道该怎么追问。

### 小结

| 层 | 管什么 | 做法 |
| --- | --- | --- |
| 工具层 | 单次查询失败 | 返回 `{"error": ...}`，不抛异常 |
| 循环层 | 任务没收敛 | 步数耗尽就降级作答 |
| 退出判断 | —— | 看有没有 tool_calls，不看 finish_reason |

## 三、产品手册问答（RAG）

### 题目要求

围绕一份产品手册做问答：按小节切分、本地向量模型编码、相似度取 top-k、交给大模型生成。要求三条：

1. 手册里写了的参数经常答错，甚至答成别的小节的内容。
2. 手册里没有的信息（比如"滤网单独买一个多少钱"），它不说不知道，而是编一个听起来很合理的答案。
3. 回答没有任何出处，没法核对哪句来自哪一节。

### 先分析

前两条都指向检索：答错说明喂进去的资料本来就错；编造说明它没意识到资料里没有。第三条说明没给引用留结构，它想标出处也无处可标。

所以考点是检索的正确性，以及用引用去约束幻觉。先把检索修对，再想办法让"有没有依据"变成一道绕不过去的关卡。

### 初版

很标准的 RAG：按 `\n## ` 切分 → `BAAI/bge-small-zh-v1.5` 编码 → 余弦相似度取 top-4 → 连问题一起交给 LLM。

### 坑一：检索方向反了

```python
top_idx = np.argsort(scores)[:TOP_K]     # 取的是最不相关的 4 段
```

`np.argsort` 默认升序，所以 `[:TOP_K]` 拿的是相似度最低的几段。这就是"手册里写了的参数却答错、甚至答成别的小节"的直接原因，它一直在把最不相关的段落喂给模型。

```python
top_idx = np.argsort(scores)[::-1][:TOP_K]   # 降序，取最相关
```

改完实测，top-1 全部命中正确小节：

```
滤网需要多久更换一次 → 滤网与更换周期 (+0.823)
睡眠模式的噪音       → 技术参数       (+0.652)
保修期多久           → 保修政策       (+0.690)
```

### 坑二：工具的"返回类型"到底怎么定

这个问题我卡了一阵。答案有点反直觉：function calling 协议里，工具根本没有"返回类型"这个字段。工具定义里的 `parameters` 描述的全是输入。在模型眼里，工具结果永远只有一种形态——一条 `{"role": "tool", "content": "<字符串>"}` 消息。

所以"定义返回类型"其实是两件事：一，Python 函数返回什么，这只是给你自己看的；二，你序列化成什么字符串喂给模型，这个才决定它看到什么。

两个结论。

**a) 别用 `str()`，用 `json.dumps(..., ensure_ascii=False)`。**

```
str()        →  ['## 滤网更换\n建议每 3 个月...']      # Python repr，单引号，不是合法 JSON
json.dumps() →  ["## 滤网更换\n建议每 3 个月..."]      # 合法 JSON
```

**b) 别返回拼好的字符串，返回带元数据的 dict。** 因为模型拿到之后要做判断：想给出处，得有小节名；想判断依据够不够，得有分数；想区分"没查到"，得有明确的结构。我原来的 `str(retrieve(...))` 这三样全没给。

于是 `match_doc` 改成返回：

```python
def match_doc(query: str) -> dict:
    hits = retrieve_with_meta(query, chunks, chunk_vecs)   # [(idx, score), ...]
    return {
        "query": query,
        "results": [
            {
                "section": section_title_of(chunks[i]),   # 出处
                "text": chunks[i],                         # 依据原文
                "score": round(float(score), 3),           # 相关度
            }
            for i, score in hits
        ],
    }
```

这个返回结构反过来逼着检索器也得改：原来的 `retrieve` 只把正文挑出来，索引和分数都丢了，现在必须一起带回来。返回结构决定了检索器要保留什么信息。

这里有条原则值得记一下：引用必须是数据里抠出来的，不能是生成出来的。如果出处是另一个模型"生成"的标题，它可能写出手册里根本没有的名字，用户一核对就对不上——引用的价值全在可核对这一点上。

### 坑三：循环结构，把上一题的经验搬过来时抄错了位置

复用了客服助手的循环骨架，结果犯了三处结构错误：

- `messages` 建在了 for 循环里面，每轮都把对话历史清零，工具结果还没用上就丢了。agent 循环的 messages 必须在循环外建、循环内累积。
- `completed` 没在循环前初始化，`UnboundLocalError`。
- `if completed: return` 和降级分支都写在了循环里，第一轮就 return，循环永远只有一轮。

另外 `for i, score in zip(hits)` 多套了一层 zip，hits 本来就是 `[(i, score), ...]`，直接 `for i, score in hits` 就行。

### 坑四：判断"依据不足"，不能只看分数

改到这里回答质量已经上来了，第三个问题（"滤网单独买一个多少钱"）模型也主动说了"资料中没有"，没有编。但出处还是没出现在回答里。

我本来想加一条机械判据：与其让模型凭感觉判断依据够不够，不如给它一条硬规则，比如最高相关度低于某个值就直说不知道。结果一校准就打脸了：

```
手册里有答案的：                手册里没答案的：
滤网多久换   → +0.823          蓝牙连接手机  → +0.450
保修期多久   → +0.690          生产厂家是谁  → +0.414
睡眠模式噪音 → +0.652          滤网多少钱    → +0.615   ← 冤
                              滤网有几种颜色 → +0.611   ← 冤
```

"滤网多少钱"（手册里没有）拿到 0.615，和"睡眠模式噪音"（手册里有）的 0.652 几乎一样高。纯按分数划线，这里就要翻车。

原因是 embedding 相似度衡量的是话题像不像，不是答案在不在。这几个没答案的问题都带"滤网"两个字，和「滤网与更换周期」话题高度重合，可问的是价格和颜色，手册里恰恰没写。相似度高，不等于事实存在。

所以"机械判据"的正解不是划线，而是强制引用：

> 每个结论后面必须标出小节名。妙处在于，模型编不出一个不存在的出处。它想编"滤网售价 99 元"，就得能指到某个小节，可哪个小节都没有这个数——引用这个动作本身就把它逼到墙角，只能承认手册里没写。

一箭双雕：既满足了给出处的要求，又用可核对的引用把幻觉压住了。这也是"用确定性检索约束 LLM 幻觉"最直接的一种落地。

### 把出处要求写进了 system prompt

规则该放在 system prompt，它是回答时必须守的规矩，不是某一轮的把控。最后写进去的是：

```python
messages = [
    {"role": "system", "content": (
        "你是产品客服，请使用 match_doc 工具查询资料来回答用户问题。"
        "回答时必须遵守两条规则："
        "1. 每个结论后面都要用「小节名」标注来源，例如「滤网与更换周期」。"
        "只能引用 match_doc 返回结果里实际存在的 section，不要编造小节名。"
        "2. 如果检索结果里找不到能支持该结论的小节，就明确回答"
        "「手册中没有相关信息」，不要根据常识推测或编造答案。"
        "如果结果的 score 很低，说明依据较弱，也应说明依据不足。"
    )},
    {"role": "user", "content": f"{question}"},
]
```

几个措辞是有意这么写的。给个例子（例如「滤网与更换周期」），是因为光说"给出处"，模型容易敷衍成末尾补一句"以上信息来自手册"，给它一个具体格式，它才知道要逐条标。强调"只能引用实际存在的 section"，是把"编出处"这条退路堵死，逼它到"没有依据就说没有"。把 score 的语义告诉它，是因为分数虽然不能拿来做硬阈值，但可以当软提示。

## 四、带记忆的个人助理（窗口与记忆）

### 题目要求

一个命令行多轮对话助理，两个记忆工具：`save_memory` 存、`search_memory` 查。对话历史存在内存的 `messages` 里，每轮连同 system prompt 一起发给模型。三个问题：

1. 聊七八轮后，忘了开头的信息和角色设定。
2. 对话一长就报「消息结构类」错误退出。
3. 重启后，工具记下的记忆基本用不上。

### 先分析

- 症状 1、2 都指向窗口裁剪：一个把不该丢的丢了，一个把结构切断了。
- 症状 3 是另一回事：记忆存是存了，但模型拿不到。

三条症状表面无关，内核一致：**裁剪和记忆都踩在「结构性约束」上**——一个踩 `messages` 的成对结构，一个踩「模型能不能真的拿到证据」。所以修法也一致：把约束变成代码里的硬规则，别交给模型或运气。

### 前提教训：我改了一行，症状全「消失」了

最先我发现，这三个问题**一个都没复现**：连聊五轮都对答如流，没崩过，重启后问「我不吃什么」也答对了。当时判断是——题目有问题，根本没有这些 bug。

原因是我动过一行。原始 `chat()` 里用户这轮的历史是累积的，我把它改成了每轮开头重建：

```python
while True:
    ...
    messages = [{"role": "system", "content": SYSTEM_PROMPT}]   # ← 我加的这行
    messages.append({"role": "user", "content": user_input})
```

这一行让历史**永远只有 2 条**（system + 当前 user）。于是：结构错触发不了裁剪，出错的前提被删了；「忘开头」也没有开头可忘，每轮都是全新开始。

这就是最该记住的一课：**症状没出现，不等于没有 bug。** 一个能跑的版本可能只是绕开了触发条件。判断 bug 在不在，要看它依赖什么条件、这些条件现在满不满足，而不是看这次跑没崩。更隐蔽的是，我这行改动本身还**加重**了症状 1——原来只是「七八轮后忘开头」，改完变成「什么都记不住」。

诊断的办法很朴素：把**每一轮真正发给模型的 `messages` 列表**打出来看角色结构。原始版本喂 12 轮，问题立刻现形。

### 坑一 + 坑二：都在 `trim`，而且同源

原始 `trim` 只有一行：

```python
def trim(messages):
    return messages[-MAX_HISTORY:]     # MAX_HISTORY = 8
```

按条数硬切，保留最后 8 条。问题就出在「任意位置切」：切掉第 0 条 → system prompt 没了（症状 1）；切在带 `tool_calls` 的 assistant 和它配对的 tool 中间 → `tool` 成了孤儿（症状 2）。

实测第 4 轮就 400 崩了：

```
round=3 全长=10 发给模型=8 结构=[assistant,tool,assistant,user,...]   ← system 没了

[!! API 报错] BadRequestError: Messages with role 'tool' must be a response
              to a preceding message with 'tool_calls'
```

README 说的「七八轮」其实是**七八条消息**——窗口小，触发很快。

这里有条硬知识：**一条 `{"role":"tool"}` 消息，必须紧跟在一条带 `tool_calls` 的 assistant 之后。** 它俩是一个整体。按条数硬切必然可能拆开它，**换个数（8→7→6）治不好，因为问题不是切多少，是切在哪。**

### 改进：两级切割，让切点落在结构边界上

**一级 · 整轮丢弃。** 一轮从一条 `user` 开始，到下一条 `user` 之前结束，`assistant/tool` 的配对全在一轮内部。所以只从 `user` 边界切，整轮整轮地丢，system 钉在最前面。

**二级 · 轮内整组丢弃。** 如果当前这一轮自己就超预算（比如用户说「帮我记住这 10 件事」，一轮里 10 次工具调用），整轮没法再丢，就在轮内丢。最小合法单位是**组**——一个 assistant + 紧随其后的若干条 tool：

```python
groups, i = [], 0
while i < len(body):
    j = i + 1
    while j < len(body) and body[j]["role"] == "tool":
        j += 1                     # 一组 = assistant(可能多个 tool_calls) + 紧跟的 tool
    groups.append(body[i:j]); i = j
# 从最老的组开始丢，user（用户的问题）绝不动
```

两级都守同一条优先级：**合法性是硬约束，长度是软预算。** 宁可少放一点历史，也不劈开配对。

这里有个边界得说清楚。我一度把原则说成「合法性 > 长度，宁可超一点」，这**只在预算是软的时候成立**。如果预算**就是**真实上下文硬上限，超一点 = 直接崩，两个都是硬约束，这时必须**合法地切**（丢组）。准确的说法是：长度要在合法性的前提下达成，达不成就合法地丢，而不是不切。本题 `MAX_HISTORY=8` 是人为调小的症状放大器，不是硬上限，所以两级就够。

### 坑三：记忆「调了白调」

这条最容易被误判。我一开始看模型**每次都调用了** `search_memory`，就以为没问题。把返回值打出来才知道：

```
记忆里明明有: {"出差行程": "下周三去上海出差", "饮食禁忌": "不吃香菜", ...}

问: 我这周有什么安排？ → 调用了 search_memory → 答: "没查到任何已有的日程安排记录"
```

调了工具，却什么都没查到。根因在匹配条件：

```python
hits = {k: v for k, v in memory.items() if keyword in k or keyword in v}
```

这是**精确子串**匹配。键存的是「出差行程」，模型查的关键词是「安排」——`"安排" in "出差行程"` 为假，返回空。**「不知道调用」和「调了白调」是两回事**，题目写的是「记忆用不上」，指的正是后者。

第一反应是「那把 `search_memory` 改成 RAG 吧」。这能跑，但方向错了：它是在给一个还没被命名的缺陷（**匹配太脆**）叠一层新机制去绕。

### 改进：注入式，把证据放进上下文

正解是把问题的前提改掉：**这么小的记忆（几十条、几 KB），根本不需要「检索」，直接全量拼进 system prompt。**

```python
def build_system_prompt() -> str:
    memory = _load_memory()
    if not memory:
        return SYSTEM_PROMPT
    lines = "\n".join(f"- {k}: {v}" for k, v in memory.items())
    return f"{SYSTEM_PROMPT}\n\n已经记住的关于用户的信息：\n{lines}"

# chat() 初始化时用它，且每轮刷新第 0 条，让本会话刚存的记忆下一轮就出现
messages = [{"role": "system", "content": build_system_prompt()}]
```

端到端验证（模拟重启后问「我这周有什么安排？」）：

```
调用: search_memory "安排"     ← 工具照旧返回空（子串还是匹配不上）
最终答: 你下周三去上海出差。   ← 但答对了
```

**工具依然返回空，答案却是对的。** 因为记忆已经作为证据躺在上下文里，模型直接从 system 读到了。「安排」和「出差行程」的语义差异，由模型自己理解——这本来就是它擅长的。

这就是减幻觉最直接的落地：**证据始终在场，而不是让模型去检索。** 检索把「信息在不在上下文」这件生死攸关的事，押在「模型猜对关键词 + 匹配算法命中」两个不确定环节上；注入则把它变成确定的。

### 大样本下该怎么设计（先想清楚，不是现在写）

注入式在「记忆塞得进上下文」时成立。真到几千条、塞不下，架构应该分三层：**核心层**（身份、硬约束）永远注入、永不淘汰，有上限；**热层**（近期高频）注入；**冷层**（其余）不注入，按需检索。每条带元数据（`importance` / `created_at` / `last_used_at` / `use_count`），淘汰用「新近度 + 频次 + 重要性」的加权分。

**为什么纯 LRU 不够**：用户第一轮说「我不吃香菜」，之后十轮聊项目。新近度判它淘汰，频次只提过一次也判它淘汰——**两个维度都说该走，可它是永久的。** 因为「多久没用」「用了多少次」量出的都是「最近活不活跃」，量不出「这条本身重不重要」。决定性的那一刻在**写入时**：`save_memory` 的时候就该给这条打上「永久 / 时效」的标签，事后从冷数据里猜不出来。

### 一处自我修正

这里得诚实记一笔。我一度把「记忆改成 RAG」说成「杀鸡用牛刀、反效果、增加幻觉」——这是**错的**，而且自相矛盾：紧接着我就在分层设计里给冷层留了检索的位置。

站得住的反对理由**只有时机一条**：症状 3 的缺陷是「子串匹配 + 从不注入」，在 4 条记忆上上 RAG 是**绕过它**，不是修它。「短查询向量区分度差」只是小规模下的副作用，不是 RAG 的普遍规律——**RAG 带出处召回，总体是降幻觉的**。

> 判断一个方案过早时，要说清反对的是哪一维——时机、规模、还是位置，别把技术本身夸大成「不对」。

## 五、几条能带走的原则

1. 失败要"返回"，不要"抛出"。工具失败应该变成模型能读的结构化观察（`{"error": ...}`），而不是让程序替它决定完蛋了。
2. 循环的退出看有没有 tool_calls，不看 finish_reason。跨厂商都成立的信号才可靠。
3. 最坏情况给降级答案，不给报错。已经确认的事实加上明确标注的缺口，比一句"出错了"有用；而在 agent 里，一句中间前言当答案比报错更危险，因为它不报错。
4. 工具的返回结构就是模型能看到的世界。它决定模型能不能给出处、能不能自我怀疑。返回拼好的字符串，等于替模型做了总结。
5. 确定性代码能干的活，别交给模型。出处的提取是字符串操作，不是生成任务。
6. 相似度不等于事实存在。靠分数阈值判断有没有答案不可靠，因为 embedding 衡量的是话题相近。更硬的约束是强制引用——编造经不起"请指出处"这一问。
7. 「没复现」不等于「没有 bug」。先问 bug 依赖什么触发条件，再看条件满不满足。一个能跑的版本可能只是绕开了触发点。
8. 结构性约束要变成代码里的硬规则。tool 必须跟 tool_calls 成对、system 必须在最前，这些是接口契约，不能在裁剪时顺手破坏。切割点要落在结构边界上，单位是"一轮"或"一组"，不是"一条"。
9. 窗口很小的时候，注入大于检索。语料大到塞不下上下文，检索才该上场。

## 六、还没做完的

- 出处约束已经写进 system prompt，但还没拿最难的用例验证过——"滤网多少钱""滤网有几种颜色"（分数高但没答案）跑一遍才能确认它没被分数骗过去。这两个顶住了，才算真的压住了幻觉。
- 客服助手还留了个小毛病：`react_answer` 里工具结果还用 `str(tc_result)` 序列化，dict 会被输出成单引号的 Python repr，改成 `json.dumps(..., ensure_ascii=False)` 更稳。
- 个人助理的 `search_memory` 现在还在被调用（会白跑一趟）。无害，先留着——它是大记忆规模时的退路。还有个语义边界要挂心上：本题丢中间组安全（`save_memory` 各自独立），但换一种"前一次检索结果喂给下一次"的依赖链，丢中间组会断推理，那时只能丢整轮。
- 现在的验证都是手挑几个问题看结果，是定性的。真要说"幻觉降了多少"，得有 golden set 和量化指标，这是下一步。

---

三道题做下来最直接的体会：让 LLM 应用可靠，不是把提示词写得更漂亮，而是给它一个结构化的世界，把边界画清楚——哪些信息真的有、哪些操作失败了、哪些结论没依据、哪句话还在上下文里。这些模型自己不会知道，得你喂给它。

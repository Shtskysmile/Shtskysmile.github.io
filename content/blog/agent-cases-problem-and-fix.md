# 从「能跑」到「可靠」：两个 Agent 应用的问题定位与改进

> [!NOTE] 这篇的来路
> 准备 Agentic AI 岗笔试时做的一组练习题，要求手写、能讲清机制。核心命题是**用 Agentic AI 减少垂直领域 LLM 幻觉**。
>
> 两道题正好覆盖 Agent 的两大形态：一道是**工具调用 + 循环**（电商客服助手），一道是 **RAG**（产品手册问答）。下面按「问题 → 分析 → 初版 → 改进」的顺序，各走一遍。

## 一、两道题要解决的问题

| | 客服助手 | 产品手册问答 |
| --- | --- | --- |
| 形态 | 工具调用 + ReAct 循环 | RAG（检索 + 生成） |
| 表面症状 | 多步问题答一半 / 不存在的单号直接崩 | 答错、编造、无出处 |
| 真正考点 | 循环的**退出条件**与**失败兜底** | 检索的**正确性**与**引用约束幻觉** |
| 共通点 | 都在问同一件事：**怎么让回答可核对、失败可解释** | |

两道题看着不一样，内核却一致：**一个不可靠的 LLM 应用，坏在"模型不知道边界在哪"**——不知道工具失败了、不知道依据够不够。所以修法方向也一致：**把边界变成模型能看见的结构化信息。**

## 二、客服助手（Agent 循环）

### 问题

题目要求做一个电商客服助手，工具只有三个：`get_order` 查订单、`get_refund_policy` 查退货政策、`list_orders_by_customer` 列客户订单。它要满足两点：

1. 只查一次的问题（"订单 A1001 的金额是多少"）基本答得对，但需要连着查好几步的问题（"客户 chen_wei 名下所有订单里，哪几件还在退货期内、各自退货扣多少手续费"），答案经常**只覆盖一部分，甚至干脆是错的——而且不报错、语气还很肯定**。
2. 问到不存在的订单号，程序**直接抛异常退出**。

### 分析

先别看代码，先想清楚这两个症状各自是什么性质：

- 「答一半却不报错」说明**循环的退出条件不可靠**——它自以为答完了，其实还在半路上。
- 「不存在的单号直接崩」说明**失败没有被翻译成模型能理解的信息**，而是变成了程序崩溃。

所以这一题的真正考点是两件事：**循环什么时候算结束**，以及**工具失败时怎么办**。方向也清楚了——把这两件事从"程序内部的状态"变成"模型能看见的观察"。

### 初版：一个朴素的 ReAct 循环

我写的循环大意是：

```python
for i in range(max_step):
    resp = client.chat.completions.create(messages=messages, tools=TOOLS, model="deepseek-chat")
    if resp.choices[0].finish_reason == 'stop':
        break                     # 模型说完了，退出
    assistant_msg = resp.choices[0].message
    messages.append(assistant_msg.model_dump())
    for tc in assistant_msg.tool_calls:
        tc_result = TOOL_IMPL[tc.function.name](**json.loads(tc.function.arguments))
        messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(tc_result)})

return resp.choices[0].message.content
```

**多步的问题确实答对了**：问"chen_wei 名下哪几件还在退货期、各扣多少手续费"，它能正确地走完——查客户订单 → 逐个查订单 → 查类目政策 → 汇总。方向没问题。

但两个要求各自都还差一口气，而这两口气，恰好就是上面分析出来的两件事。

### 改进

#### 坑 1：崩在"工具失败"，而我以为是"循环失败"

实测查一个不存在的单号：

```
CRASHED: KeyError 'A9999'
```

我第一反应是加兜底，于是在**循环之后**补了一句：

```python
if resp.choices[0].finish_reason != 'stop':
    return "There is some err of getting result"
```

**结果照样崩。** 原因很关键：异常是在**循环内部** `get_order('A9999')` 那一行抛出来的，Python 遇到未捕获异常会立刻向上弹出——循环后面的兜底代码根本轮不到执行。

> **教训**：兜底必须站在异常的**必经之路**上。这个循环有三个出口：模型收敛、步数耗尽、**工具抛异常**。我守了前两个，漏了第三个——而崩溃恰恰是从第三个走的。

#### 坑 2：退出条件用错了信号

我原本靠 `finish_reason == 'stop'` 判断"做完了"。但 `finish_reason` 描述的是**"模型这一轮想干什么"**，取值还有 `length`（被截断）、`content_filter` 等。模型明明答完了，却因为输出被截断而 `finish_reason == 'length'`，就会被误判成"没完"，白跑一轮。

**更可靠的信号是：这一轮有没有 `tool_calls`。** 模型不请求工具，就说明它准备用现有信息说话了——这个信号跨厂商都成立。

顺带发现，如果循环走满 `max_step`，我返回的 `resp` 是**最后一轮**的，而它的 `content` 很可能是句没写完的前言：

```python
# finish_reason == 'tool_calls' 那一轮，message.content 实测长这样：
"I'll look up the details for order A1001."
```

也就是说，**循环耗尽时我会把一句中间前言当成答案交给用户**——不报错、语气还肯定。这正是题目里"答案只覆盖一部分、而且不报错"的症状来源之一。

#### 改进一：工具层——失败要"返回"，不要"抛出"

数据访问层不该把裸 `KeyError` 漏给上层。所以修在工具实现里：

```python
def get_order(order_id: str) -> dict:
    order = ORDERS.get(order_id)
    if order is None:
        return {"error": f"订单号 {order_id} 不存在，请确认后重试"}
    return order
```

关键不在于"不崩"，而在于**结果是喂给模型的字符串**：带着 `error` 字段回到 `role: "tool"` 的消息里，模型读得懂，自己就会改口——

> 抱歉，订单号 A9999 不存在，我无法查询到它的金额。请确认订单号是否正确……

**这是减少幻觉最直接的一招：把"失败"变成模型能推理的一条普通观察，而不是让程序替它决定"完蛋了"。** 幻觉常常就源于模型根本不知道前提已经失败。

#### 改进二：循环层——换退出信号 + 降级作答

两处改动：

```python
completed = False
for _ in range(max_step):
    resp = client.chat.completions.create(messages=messages, tools=TOOLS, model="deepseek-chat")
    assistant_msg = resp.choices[0].message

    if not assistant_msg.tool_calls:      # ← 退出判据：没有工具调用 = 准备作答
        completed = True
        break
    # ... 执行工具、追加 tool 消息 ...

if completed:
    return assistant_msg.content

# 步数耗尽：不再给 tools，让模型基于已有信息降级作答
messages.append({
    "role": "user",
    "content": "工具调用次数已达上限，你无法再查询新信息。"
               "请仅根据上面已经获得的结果作答，并明确说明哪些部分尚未查到或无法确认。",
})
final = client.chat.completions.create(model="deepseek-chat", messages=messages)  # 注意：不带 tools
return final.choices[0].message.content
```

**降级作答的实测效果**（临时把 `max_step=1` 强制触发）：

> 目前我仅查到客户 chen_wei 名下有 **2 笔订单**：A1001 和 A1002。但由于工具调用次数已达上限，我**无法继续查询**……所以关于"哪几件还在退货期内"，我目前**无法确认，无法给出答案**。

这就是一个 agent 在最坏情况下该有的样子：**给出已确认的部分事实 + 明确标注缺口**，而不是一句没有信息量的报错，更不是硬编一个答案。用户至少知道"有 2 笔订单但详情没查到"，也就知道该怎么追问。

#### 小结：三层防护，各管一段

| 层 | 管什么 | 手段 |
| --- | --- | --- |
| 工具层 | 单次查询失败 | 返回 `{"error": ...}`，不抛异常 |
| 循环层 | 任务没收敛 | 步数耗尽 → 降级作答 |
| —— | —— | 退出靠"有无 tool_calls"，不靠 `finish_reason` |

## 三、产品手册问答（RAG）

### 问题

题目要求围绕一份产品手册做问答机器人：按小节切分手册 → 本地向量模型编码 → 相似度取 top-k → 交给大模型生成。要满足三点：

1. 手册里明确写了的参数**经常答错**，甚至答成别的小节的内容。
2. 手册里**没有**的信息（比如"滤网单独买一个多少钱"），它不会说不知道，而是**编一个听起来很合理的答案**。
3. 回答**没有任何出处**，无法核对哪句话来自手册哪一节。

### 分析

两个症状都指向**检索环节**：答错说明喂进去的资料就是错的；编造说明它压根没意识到"资料里没有"。而"没有出处"说明**没有给引用留结构**——它想标出处也无处可标。

所以这题的真正考点是**检索的正确性**和**引用对幻觉的约束**。方向：先把检索修对，再想办法让"有没有依据"变成一道模型绕不过去的关卡。

### 初版：标准 RAG 管线

流程很直白：按 `\n## ` 切分手册 → `BAAI/bge-small-zh-v1.5` 编码 → 余弦相似度取 top-4 → 连同问题交给 LLM。三项要求写进了期望：只在有依据时作答、给出处、没依据要说"没有"。

### 改进

#### 坑 1：检索方向反了（最致命的一个）

```python
top_idx = np.argsort(scores)[:TOP_K]     # ← 取的是最不相关的 4 段
```

`np.argsort` **默认升序**，所以 `[:TOP_K]` 拿的是相似度**最低**的几段。这就是"手册里写了的参数却答错、甚至答成别的小节"的直接原因——**它一直在把最不相关的段落喂给模型**。

```python
top_idx = np.argsort(scores)[::-1][:TOP_K]   # 降序，取最相关
```

修完后实测 top-1 全部命中正确小节：

```
滤网需要多久更换一次 → 滤网与更换周期 (+0.823)
睡眠模式的噪音       → 技术参数       (+0.652)
保修期多久           → 保修政策       (+0.690)
```

#### 坑 2：工具的"返回类型"到底怎么定？

这是我卡住过的问题，答案有点反直觉：**function calling 协议里，工具根本没有"返回类型"字段。** 工具定义（`parameters`）描述的全是**输入**。模型的视角里，工具结果永远只有一种形态：一条 `{"role": "tool", "content": "<字符串>"}` 消息。

所以"定义返回类型"实际是两件事：①Python 函数返回什么（只给你自己看）；②**你序列化成什么字符串喂给模型**（这才决定模型看到什么）。

两个结论：

**（a）别用 `str()`，用 `json.dumps(..., ensure_ascii=False)`。**

```
str()        →  ['## 滤网更换\n建议每 3 个月...']      # Python repr，单引号，不是合法 JSON
json.dumps() →  ["## 滤网更换\n建议每 3 个月..."]      # 合法 JSON
```

**（b）别返回拼好的字符串，要返回带元数据的 dict。** 因为模型拿到之后要做决策——想给出处，得有**小节名**；想判断"依据够不够"，得有**分数**；想区分"没查到"，得有明确的结构。这些我原来的 `str(retrieve(...))` 全没给。

于是 `match_doc` 返回：

```python
def match_doc(query: str) -> dict:
    hits = retrieve_with_meta(query, chunks, chunk_vecs)   # [(idx, score), ...]
    return {
        "query": query,
        "results": [
            {
                "section": section_title_of(chunks[i]),   # 出处
                "text": chunks[i],                         # 依据原文
                "score": round(float(score), 3),           # 相关度
            }
            for i, score in hits
        ],
    }
```

**这个返回结构倒逼了检索器的改造**：`retrieve` 原来只把正文挑出来，丢掉了索引和分数；现在必须一起带回来。**返回结构定义了检索器要保留什么信息**——这是设计，不是麻烦。

至于"出处"怎么取，其实是一行字符串操作，**不该用 LLM**：

```python
def section_title_of(chunk: str) -> str:
    return chunk.split("\n", 1)[0].strip().lstrip("#").strip()
```

因为切分符 `\n## ` 已被切掉，**每个 chunk 的第一行就是小节标题本身**。

> 这里有个值得记住的原则：**引用必须是数据里抠出来的，不能是生成出来的。** 如果出处是另一个模型"生成"的标题，它可能写出手册里根本不存在的名字，用户核对时对不上——引用的价值就在于**可核对**。确定性代码能干的活，别交给模型。

#### 坑 3：循环结构（把上一题的经验搬过来时抄错了位置）

复用了客服助手的循环骨架，但犯了三处结构错误：

- **`messages` 建在了 for 循环里面** → 每一轮都把对话历史清零，工具结果还没用上就被丢了。**agent 循环的 `messages` 必须在循环外建、循环内累积。**
- `completed` 没在循环前初始化 → `UnboundLocalError`。
- `if completed: return` 和降级分支都写在了**循环内** → 第一轮就 `return`，循环永远只有一轮。

另外 `for i, score in zip(hits)` 是多余的一层 `zip`——`hits` 已经是 `[(i, score), ...]`，直接 `for i, score in hits`。

#### 坑 4：判断"依据不足"，不能只靠分数

改进后回答质量上来了，第三个问题（"滤网单独买一个多少钱"）模型也**主动说了"资料中没有"**，没编。但出处还没出现在回答里。

于是我想加一条"机械判据"：与其让模型凭感觉判断依据够不够，不如给它一条硬规则，比如"最高相关度低于某值就直说不知道"。**但一校准就打脸了**：

```
手册里【有】答案的：            手册里【没有】答案的：
滤网多久换   → +0.823          蓝牙连接手机  → +0.450
保修期多久   → +0.690          生产厂家是谁  → +0.414
睡眠模式噪音 → +0.652          滤网多少钱    → +0.615   ← 冤
                              滤网有几种颜色 → +0.611   ← 冤
```

**"滤网多少钱"（手册里没有）拿到的 0.615，和"睡眠模式噪音"（手册里有）的 0.652 几乎一样高。** 纯按分数划线会在这里翻车。

**原因**：embedding 相似度衡量的是**话题像不像**，不是**答案在不在**。这几个没答案的问题都带"滤网"二字，和「滤网与更换周期」话题高度重合——但问的是价格/颜色，手册里恰恰没写。**相似度高 ≠ 事实存在。**

所以"机械判据"的正解不是划一条线，而是**强制引用**：

> 要求每个结论后面必须标出小节名。**妙处在于：模型编不出一个不存在的出处。** 想编"滤网售价 99 元"，它得能指到某个小节，可哪个小节都没有这个数——引用这个动作本身就把它逼到墙角，只能承认"手册无此信息"。

**一箭双雕**：既满足"给出处"的要求，又用可核对的引用压住了幻觉。这正是命题里"用确定性检索约束 LLM 幻觉"最直接的落地。

## 四、提炼出来的几条通用原则

1. **失败要"返回"，不要"抛出"。** 工具失败应变成模型能读的结构化观察（`{"error": ...}`），而不是让程序替它决定"完蛋了"。幻觉常常源于模型不知道前提已经失败。

2. **循环的退出看"有没有 tool_calls"，不看 `finish_reason`。** 跨厂商都成立的信号才可靠。

3. **最坏情况要给"降级答案"，不给报错。** 已确认的事实 + 明确标注的缺口，比一句"出错了"有用得多；而在 agent 里，一句中间前言当答案，比报错更危险，因为它不报错。

4. **工具的返回结构 = 模型能看到的世界。** 它决定模型能不能给出处、能不能自我怀疑。返回拼好的字符串，等于替模型做了总结，剥夺了它"依据不足"的能力。

5. **确定性代码能干的活，别交给模型。** 出处的提取是字符串操作，不是生成任务。引用必须可核对。

6. **相似度不等于事实存在。** 靠分数阈值判断"有没有答案"不可靠，因为 embedding 衡量的是话题相近，不是答案在不在。更硬的约束是**强制引用**——编造经不起"请指出出处"这一问。

## 一、Transformer

### 1.1 整体架构

Transformer 由 **Encoder（编码器）** 和 **Decoder（解码器）** 堆叠而成，核心创新是用**自注意力（Self-Attention）**替代 RNN 的循环结构，实现完全并行化。

```
输入序列 → Input Embedding + Positional Encoding
         → [Encoder × 6 层] → 编码后的表示
         → [Decoder × 6 层] → 逐 token 输出 → 最终序列
```

### 1.2 为什么需要 Positional Encoding

Self-Attention 本身**对位置不敏感**——"我爱你"和"你爱我"的注意力计算没有区别。Positional Encoding 给每个位置注入位置信号，原文用正弦/余弦函数：

```python
PE(pos, 2i)   = sin(pos / 10000^(2i/d_model))
PE(pos, 2i+1) = cos(pos / 10000^(2i/d_model))
```

这种设计让模型可以通过相对偏移（pos+k 的 PE 是 pos 的线性函数）推断相对位置。

> 注：现代 LLM（LLaMA、Qwen、DeepSeek、Mistral 等）几乎都改用 **RoPE 旋转位置编码**（只有 Transformer 原文和 BERT 用绝对位置编码），详见第六章。

### 1.3 Encoder 内部结构

每层 Encoder 包含两个子层，每个子层都有 **残差连接 + LayerNorm**：

```
Input → Self-Attention → Add & Norm → Feed-Forward → Add & Norm → Output
```

- **Self-Attention（自注意力）**：每个 token 关注整个序列的所有 token，计算上下文相关的表示
- **Feed-Forward**：两层全连接 + ReLU 激活，每个位置独立变换

### 1.4 Decoder 内部结构

每层 Decoder 包含**三个**子层：

```
Input → Masked Self-Attention → Add & Norm → Cross-Attention → Add & Norm → FFN → Add & Norm → Output
```

- **Masked Self-Attention（因果注意力）**：只能看当前位置**及之前**的 token，不能偷看后面的词
- **Cross-Attention（编解码器注意力）**：Q 来自 Decoder，K、V 来自 Encoder 的输出，把输入和生成连接起来
- **FFN**：同 Encoder

### 1.5 Self-Attention 核心公式

```
Attention(Q, K, V) = softmax(QK^T / √d_k) × V
```

- **Q（Query）**：当前 token 在"查什么信息"
- **K（Key）**：每个 token "身上有什么标签供别人查找"
- **V（Value）**：被查到后"提供什么实际信息"
- **√d_k（缩放因子）**：防止点积过大导致 softmax 梯度消失

### 1.6 Multi-Head Attention

一个注意力头只能捕获一种关系模式。多头注意力并行跑多个头，每个头在不同子空间学习不同的关系：

```
MultiHead(Q, K, V) = Concat(head_1, ..., head_h) × W^O

head_i = Attention(QW_i^Q, KW_i^K, VW_i^V)
```

例如翻译"bank"：一个头关注上下文判断是"银行"还是"河岸"，另一个头关注语法搭配。

### 1.7 面试要点

| 考点                             | 答案要点                                                                     |
| -------------------------------- | ---------------------------------------------------------------------------- |
| Transformer 相比 RNN/LSTM 的优势 | 并行计算、长距离依赖、无梯度消失（残差）                                     |
| 为什么用 √d_k                   | d_k 越大点积方差越大，softmax 推向饱和区，梯度消失                           |
| Self-Attention 时间复杂度        | O(n²·d)，n 为序列长度，d 为维度                                            |
| LayerNorm vs BatchNorm           | LayerNorm 对每个样本的特征维归一化，适合变长序列                             |
| 残差连接的作用                   | 梯度有一条恒等捷径直接回传，缓解深层梯度消失；模型只需学"增量"               |
| Q/K 同维、V 可不同               | 点积要求 Q、K 维度一致；V 维度可不同，多头拼接后再线性投影                   |
| FFN 为什么是 4×d_model          | 两段式"升维再降维"提升非线性表达容量，经验性最优宽度                         |
| padding mask vs 因果 mask        | padding mask 忽略无效填充 token；因果 mask 禁止看未来；训练时两者叠加        |
| O(n²) 注意力怎么优化            | FlashAttention（分块+在线 softmax+IO 感知）、稀疏/线性注意力、MoE+局部注意力 |

### 1.8 FlashAttention（面试高频：O(n²) 怎么被打的）

**背景：注意力慢不是慢在算，是慢在"搬"。** GPU 有两级存储——HBM（显存，大但慢）与 SRAM（片上缓存，小但快几十倍）。标准实现（PyTorch MultiheadAttention / cuBLAS）每一步都把中间结果写回 HBM 再读回：

```
算 QK^T → n×n 注意力矩阵 S → 写回 HBM
softmax(S) → 读回 → 写回 HBM
×V → 输出 → 写回 HBM
```

序列一长，n×n 矩阵在 HBM/SRAM 间反复搬运 → **瓶颈是显存带宽，不是 FLOPs**。所以长序列提速的关键是"少搬数据"。

**三个核心技巧：**

1. **分块（Tiling）**：Q/K/V 切成小块，一次只把一个块读进 SRAM，算完输出写回。**永远不把 n×n 注意力矩阵物化到 HBM** → 显存 O(n²)→O(n)。
2. **在线 Softmax（关键突破）**：softmax 需要全局 max 和 sum，分块后一次算不全。用"运行最大值 + 重缩放"渐进逼近：每块用新 max 重缩放已累积部分，最后与标准 softmax **数学等价**。
3. **IO 感知（I/O-aware）**：按"数据搬运量"而非 FLOPs 优化，最大化 SRAM 复用、最小化 HBM 读写。

**效果**：显存 O(n²)→O(n)（不物化注意力矩阵）；训练提速 1.7~2×（长序列更多）；可塞更大 batch / 更长上下文。**FlashAttention-2** 优化并行策略（序列维并行 + 减少非矩阵乘部分），再快 ~2×。

**面试问答：**

| 考点             | 答案                                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 为什么快         | 按 I/O（数据搬运）优化，不是按 FLOPs；最大化 SRAM 复用、最小化 HBM 读写                                                             |
| 省多少显存       | 不物化 n×n 注意力矩阵，O(n²)→O(n)                                                                                                |
| 结果一样吗       | 数学等价，只是换执行方式（和 KV Cache 同哲学："改执行，不改结果"）                                                                  |
| 和 KV Cache 关系 | **互补**：FlashAttention 打 O(n²) 计算/显存；KV Cache 解决 decode 阶段历史重复计算。一个管前向计算本身，一个管解码别重算历史 |
| 为什么之前没人做 | cuBLAS 只会矩阵乘法，注意力含 softmax/mask 等非矩阵乘操作，分块实现难写对；在线 softmax 是绕开这个坎的关键                          |

## 二、BERT

### 2.1 核心定位

**B**idirectional **E**ncoder **R**epresentations from **T**ransformers

**Encoder-only** 架构，用于**自然语言理解（NLU）**，擅长"读懂"文本而非"生成"文本。

### 2.2 架构

```
输入文本 → Input Embedding（Token + Segment + Position）
         → [Transformer Encoder × 12/24 层]
         → 每个 token 输出一个上下文表示
```

- **BERT-base**: 12 层, 768 维, 12 头, 1.1 亿参数
- **BERT-large**: 24 层, 1024 维, 16 头, 3.4 亿参数

### 2.3 输入表示（三个 Embedding 求和）

```
Input = Token Embedding + Segment Embedding + Position Embedding
```

- **Token Embedding**: WordPiece 分词，`[CLS]` 开头（聚合整句语义），`[SEP]` 分隔句子
- **Segment Embedding**: 区分句子 A / 句子 B（用于句对任务）
- **Position Embedding**: **可学习**的位置嵌入（不是 Transformer 的正弦函数）

### 2.4 预训练任务

**（1）MLM（Masked Language Model）——完形填空**

随机 mask 掉 15% 的 token，让模型根据**双向上下文**预测被 mask 的词：

- 80% 替换为 `[MASK]`
- 10% 替换为随机词
- 10% 保持原词（防止模型只学 `[MASK]` 的表示）

**（2）NSP（Next Sentence Prediction）——句对关系判断**

判断句子 B 是否是句子 A 的下一句（50% 是，50% 不是），用 `[CLS]` 的表示做二分类。

> 注：后续研究（RoBERTa）证明 NSP 不是必需的，删掉 NSP 并增大数据量效果更好。

### 2.5 下游任务微调

```
CLS → Linear Classifier         → 文本分类 / 情感分析
每个 token → Linear + Softmax    → 命名实体识别（NER）
两个句子 → CLS → 二分类           → 文本匹配 / NLI
句子 → 从上下文中找答案 span      → 抽取式问答（SQuAD）
```

### 2.6 与 GPT 的核心区别

|                      | BERT                   | GPT                    |
| -------------------- | ---------------------- | ---------------------- |
| **架构**       | Encoder-only           | Decoder-only           |
| **注意力**     | 双向（同时看左右）     | 单向因果（只看左边）   |
| **预训练目标** | MLM（猜被遮住的词）    | LM（猜下一个词）       |
| **擅长**       | 理解：分类、匹配、抽取 | 生成：对话、续写、翻译 |
| **微调**       | 必须微调               | 可以 zero/few-shot     |

### 2.7 BERT 的实际应用

- 文本分类（情感分析、意图识别）
- 命名实体识别（NER）
- 语义匹配（搜索排序、问答匹配）
- 抽取式问答（从文本中找答案 span）
- 搜索引擎查询理解（Google 2019 年起使用）

### 2.8 面试要点

| 考点                      | 答案要点                                                                    |
| ------------------------- | --------------------------------------------------------------------------- |
| "双向"怎么实现            | MLM 预训练时每个 token 能看到整个上下文，没有因果掩码                       |
| 为什么不用 BERT 做生成    | MLM 目标是完形填空，不是自回归预测下一篇。强行生成质量很差                  |
| [CLS] 的作用              | 聚合整个输入序列的语义，用于分类任务                                        |
| BERT 输入长度限制         | 原始 512 token（位置嵌入只训了 512 个），长文本需要截断或分段               |
| RoBERTa/ALBERT 改进了什么 | RoBERTa 去 NSP+动态 mask+更大数据；ALBERT 嵌入分解+跨层参数共享，大幅省参数 |
| WordPiece 是什么          | 子词级分词：常见词整词、罕见词拆子词，解决 OOV；词表外词也能表示            |
| BERT 的缺点               | 参数量大、推理慢；预训练用 [MASK] 与推理输入不一致（mask 不匹配）           |

## 三、GPT 与 Decoder-Only 架构

### 3.1 GPT 全称

**G**enerative **P**re-trained **T**ransformer

只用 Transformer 的 **Decoder** 部分，做自回归语言建模。

### 3.2 架构

GPT 的 Decoder 只有**两个**子层（原始 Transformer 的 Decoder 有三个）：

```
原始 Transformer Decoder:          GPT Decoder:
1. Masked Self-Attention      →   1. Masked Self-Attention
2. Cross-Attention (删掉!)    →   2. Feed-Forward Network
3. Feed-Forward Network
```

**Cross-Attention 被砍掉**，因为没有 Encoder 可看。Decoder 的输入和输出是同一段文本。

### 3.3 各版本规模

|                      | GPT-1   | GPT-2 | GPT-3   | GPT-4                   |
| -------------------- | ------- | ----- | ------- | ----------------------- |
| **参数量**     | 1.17 亿 | 15 亿 | 1750 亿 | 未公开（~1.8 万亿传闻） |
| **层数**       | 12      | 48    | 96      | -                       |
| **上下文长度** | 512     | 1024  | 2048    | 8K/32K/128K             |

### 3.4 核心机制：因果注意力（Masked Self-Attention）

```
原始注意力矩阵:        加上因果掩码后（下三角）:
  t1  t2  t3          t1    t2    t3
t1[a,  b,  c]      t1[a,   -∞,   -∞]
t2[d,  e,  f]  →   t2[d,    e,   -∞]
t3[g,  h,  i]      t3[g,    h,    i]
```

每个 token 只能关注**自己及前面**的 token。`-∞` 经过 softmax 后权重变为 0。

### 3.5 预训练目标

最简单的语言建模：**给定上文，预测下一个词**

```
L = -Σ log P(x_t | x_1, x_2, ..., x_{t-1})
```

不需要 BERT 的 MLM（随机 mask），不需要 NSP，一个目标函数训到底。

### 3.6 训练流程的三个阶段

```
1. 预训练（Pre-training）：海量无标注文本，语言建模目标，学到通用语言能力
       ↓
2. 监督微调（SFT）：高质量指令-回复对，学会对话格式和遵循指令
       ↓
3. 人类反馈强化学习（RLHF）：人类标注偏好 → 训练奖励模型 → PPO 优化，对齐人类偏好
```

> 注：这是"最小流水线"。现代 LLM 的完整流水线还要加上：多阶段预训练（第七章）、DPO/GRPO 等新对齐方法（第八章）、以及工具调用等能力特化（第九章）。

### 3.7 解码策略

| 策略                  | 原理                                 | 特点                         |
| --------------------- | ------------------------------------ | ---------------------------- |
| **贪心解码**    | 每一步选概率最大的 token             | 确定性输出，容易重复         |
| **Beam Search** | 保留 top-k 个候选序列                | 适合翻译等需要全局最优的任务 |
| **Top-k 采样**  | 从概率最高的前 k 个 token 中随机采样 | 增加多样性                   |
| **Top-p 采样**  | 从累积概率 ≥ p 的最小集合中采样     | 动态调整候选数               |
| **温度**        | softmax 前将 logits 除以温度 T       | T<1 更确定，T>1 更随机       |

### 3.7.1 温度与 top-k / top-p 的关系（面试高频）

**温度控制分布"尖锐程度"**：`p_i = softmax(z_i / T)`

- **T > 1**：logits 被压缩，分数差距变小 → 分布变平、接近均匀 → 采样更随机、更多样
- **T < 1**：logits 被放大，差距拉开 → 分布变尖、趋近 one-hot → 几乎只抽最高分
- **极限**：T→∞ 均匀分布（最随机）；T→0 退化为 argmax（完全确定）

**数值直觉**（logits = [3.0, 2.0, 1.0, 0.0]）：

| 温度 | P(3.0) | P(2.0) | 行为           |
| ---- | ------ | ------ | -------------- |
| 0.5  | 88%    | 12%    | 几乎只选最高分 |
| 1    | 73%    | 27%    | 正常           |
| 2    | 62%    | 38%    | 越来越接近随机 |

**温度影响 top-k 吗？——"不影响选谁，影响选中后怎么抽"**

- **候选集合不变**：top-k 取分数最高的 k 个；除以 T（T>0）是单调变换，分数排序不变，所以集合永远是那 k 个。
- **集合内概率仍受温度影响**：采样在 top-k 内按 softmax(logits/T) 抽，T 大 → 内部抽得均匀，T 小 → 高度偏向第一名。
- **边界情况**：top-k=1（候选集只有一个）或贪心解码（无采样）→ 温度完全无效。

**top-p vs top-k（关键区别）**：

| 采样方式                          | 温度是否改变候选集合                                                                                      |
| --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| top-k（固定 k 个最高分）          | **不变**（排序单调）                                                                                |
| top-p（累积概率 ≥ p 的最小集合） | **会变**：温度大 → 分布平 → 需要更多 token 才凑够累积概率，集合变大；温度小 → 分布尖 → 集合变小 |

### 3.8 面试要点

| 考点                                 | 答案要点                                                                                          |
| ------------------------------------ | ------------------------------------------------------------------------------------------------- |
| GPT 为什么没有 Cross-Attention       | 没有 Encoder，输入输出是同一段文本，Self-Attention 已足够                                         |
| 为什么 Decoder-Only 成为主流         | 参数利用率高、训练效率高（每个 token 都贡献梯度）、涌现 In-Context Learning、推理时 KV Cache 高效 |
| 纯 Decoder 比 Encoder-Decoder 好在哪 | 见"纯 Decoder 优势"章节                                                                           |
| 涌现能力是什么                       | 规模过阈值后突然出现的泛化能力（ICL/CoT）；有争议，可能是度量方式导致的平滑变化                   |
| 上下文窗口为什么有限                 | 位置编码、注意力 O(n²)、KV 显存共同限制；扩展靠 RoPE + 长文继续预训练                            |
| 特殊 token 有什么用                  | <s></s>/<eos></eos>/<                                                                             |
| 为什么预训练学不会问答               | 语言建模只学"下一个词"统计规律；格式靠 SFT、偏好靠 RL 教                                          |
| 温度为什么能让输出更随机             | 除以 T 压缩/放大分数差距：T>1 分布变平接近均匀 → 采样更多样；T<1 变尖趋近 argmax                 |
| 温度影响 top-k 吗                    | 不影响"选谁"（单调变换，分数排序不变），只影响 top-k 集合内的采样分布；k=1 或贪心时温度无效       |
| top-k 和 top-p 对温度的敏感性        | top-k 候选集合不变；top-p 候选集合会随温度变（分布平 → 需要更多 token 才凑够累积概率）           |

## 四、纯 Decoder 架构的优势

### 4.1 参数利用率

Encoder-Decoder 把参数分成"读"和"写"两半。Decoder-Only **所有参数既参与理解也参与生成**，同样参数量的实际利用率更高。

### 4.2 训练效率

|                       | 每个 token 都是训练信号？  | 利用率 |
| --------------------- | -------------------------- | ------ |
| GPT（LM）             | ✓ 每个 token 都预测下一个 | 100%   |
| BERT（MLM）           | ✗ 只有被 mask 的 15%      | 15%    |
| T5（span corruption） | ✗ 被 mask 的 ~20%         | 20%    |

同样的数据和算力，GPT 的训练信号量是 BERT 的 5-7 倍。

### 4.3 In-Context Learning 的涌现

因果语言模型训练中反复看到"前面几个相似 pattern → 后面类似输出"的模式，学会了从上下文里"拷贝"范式——这就是 zero-shot 和 few-shot 能力的来源。双向模型没有从左到右的生成压力，学不到这个能力。

### 4.4 目标函数简单

```
GPT:  预测下一个 token             ← 一个损失，无超参数
T5:   还要设计噪声方案（mask 比例、span 长度、调度策略）
BERT: 还要平衡 MLM 和 NSP 权重
```

简单 = 更容易 scale。用更大算力和更多数据就能直接更好。

### 4.5 推理效率：KV Cache

Decoder-Only 的 KV Cache 非常干净。Encoder-Decoder 每次生成新 token 都要在 Encoder 输出上重新做 Cross-Attention，对于万级 token 的上下文，累积开销巨大。

### 4.6 面试要点

| 考点                     | 答案要点                                                     |
| ------------------------ | ------------------------------------------------------------ |
| Decoder-Only 参数利用率  | 所有参数既参与理解也参与生成，不分成"读"与"写"两半           |
| 训练信号为什么比 BERT 多 | 每个 token 都预测下一个 → 100% 信号；BERT 只有 mask 的 15%  |
| ICL 能力从哪来           | 因果训练反复见"相似 pattern → 后续输出"，学会上下文拷贝范式 |
| 为什么更容易 scale       | 目标简单、旋钮少、loss 随规模幂律可外推                      |
| 推理为什么更干净         | 无 cross-attention，KV Cache 简单，长上下文累积开销小        |

## 五、KV Cache

### 5.1 问题

自回归生成时，每生成一个新 token，都要对**所有历史 token** 重新计算 Self-Attention。生成到第 N 个 token 时，前面的 N-1 个 token 的 K 和 V 被重复算了 N-1 次。

### 5.2 方案

**K 和 V 只算一次，缓存起来。新 token 的 Q 直接查历史 KV。**

```python
K_cache, V_cache = [], []

for step in range(max_new_tokens):
    # 只算当前这一个 token 的 Q、K、V
    q, k, v = compute_qkv(current_token)
  
    # K 和 V 追加到缓存
    K_cache = concat(K_cache, k)
    V_cache = concat(V_cache, v)
  
    # 注意力：用当前 Q 去查所有历史 K、V
    output = softmax(q @ K_cache.T / sqrt(d)) @ V_cache
  
    next_token = sample(output)
```

### 5.3 关键细节

- **Q 不缓存**：Q 只代表当前 token 想查什么，历史 token 的 Q 对新 token 无用
- **K 缓存**：每个 token 被查时需要它的 K 来匹配（这个 token"身上有什么特征供别人查"）
- **V 缓存**：每个 token 被查到后需要它的 V 来提供实际信息（"被查到后给什么内容出去"）
- **每层独立缓存**：32 层的模型需要 32 组独立的 KV Cache

### 5.4 显存代价

以 LLaMA-2 7B（32 层, 4096 维）为例：

| 上下文长度  | KV Cache 显存 |
| ----------- | ------------- |
| 1K tokens   | ~0.5 GB       |
| 4K tokens   | ~2 GB         |
| 32K tokens  | ~16 GB        |
| 128K tokens | ~64 GB        |

长上下文时 KV Cache 成为显存瓶颈。

### 5.5 优化方案

| 技术                                     | 原理                                   | 效果                    |
| ---------------------------------------- | -------------------------------------- | ----------------------- |
| **MQA**（Multi-Query Attention）   | 所有注意力头共享一组 K、V              | KV Cache 缩小为 1/heads |
| **GQA**（Grouped Query Attention） | 每组 Q 头共享一组 KV                   | 折中方案，效果接近 MHA  |
| **PagedAttention**（vLLM）         | 把 KV Cache 分页管理，类似 OS 虚拟内存 | 减少碎片，提高吞吐量    |
| **量化 KV Cache**                  | KV 存 INT8 而非 FP16                   | 显存减半                |

### 5.6 Prefill（预填充）与 Decode（解码）

自回归推理可以拆成两个阶段，瓶颈完全不同：

|                    | Prefill（预填充）                                          | Decode（解码）                                               |
| ------------------ | ---------------------------------------------------------- | ------------------------------------------------------------ |
| **做什么**   | 一次性处理整个输入 prompt，并行算出所有位置的 K/V 写入缓存 | 逐 token 生成，每步只算一个新位置                            |
| **计算形态** | 大矩阵乘法，**计算密集**                             | 计算量小但**串行**，每步要读一遍整个 KV Cache          |
| **瓶颈**     | 吞吐（FLOPs / 显存带宽）                                   | **访存带宽**（I/O bound）+ 时延                        |
| **常见优化** | chunked prefill（把长 prompt 分块算）、连续批处理          | KV 量化、GQA/MLA 减缓存、投机解码（小模型草稿 + 大模型验证） |

面试时能说出"prefill 是算力瓶颈、decode 是访存瓶颈"会非常加分。

### 5.7 投机解码（Speculative Decoding）

decode 是访存瓶颈：每步只算一个 token 却要读一遍整个 KV Cache。投机解码用"小模型快猜 + 大模型并行验证"把串行生成变并行：

```
1. 小模型（draft model）逐 token 快速生成 k 个候选
2. 大模型一次前向【并行】算这 k 个位置的 logits（一条大矩阵乘）
3. 逐位置比对：候选与大模型一致 → 直接接受；第一个不一致处截断，换成大模型的 token
4. 接受率越高，加速越多（LLaMA-2 70B 约加速 2x）
```

**为什么能并行**：decode 的"串行"只是采样依赖，logits 计算本身一次可处理多个位置；大模型一次前向同时算 k 个 token，把 k 次"读 KV + 小矩阵乘"换成 1 次大矩阵乘，访存开销摊薄。

**代价**：小模型额外前向成本；变体 EAGLE / MEDUSA 用模型自身预测草稿，避免另训小模型。

**为什么它"不掉精度"（面试加分点）**：接受是概率性的——对草稿模型提出的 token，以 `min(1, p_目标 / p_草稿)` 的概率接受，拒绝时从修正后的分布重采样。这样采样结果与直接用目标模型**分布完全一致（lossless）**，不是近似加速，所以部署能放心用。

**来源**：2022 年底 Google（Leviathan et al., arXiv 2211.17192）与 DeepMind（Chen et al., arXiv 2302.01318）**独立同时**提出；思想可追溯到 Blockwise Parallel Decoding（Stern et al., NeurIPS 2018，多预测头一次并行预测多个未来 token）。变体 Medusa / EAGLE 在目标模型上加预测头或复用其内部特征做草稿，免去单独训练小模型。

**面试一句话**：投机解码 = 小模型草稿 + 大模型验证，用"计算换访存"，把访存密集的串行 decode 变成计算密集的并行验证。

### 5.8 MLA（Multi-head Latent Attention）—— DeepSeek 的 KV Cache 压缩方案

> MLA 由 DeepSeek-V2 提出、DeepSeek-V3 沿用，是整个 DeepSeek 低成本路线的基石之一（呼应 14.2）。它回答的核心问题是：**GQA 只省了"头数"，能不能连"维度"一起省？**

**背景：MHA / GQA / MLA 各自怎么省**

| 方案 | 做法                                 | 省的是什么     | 代价                       |
| ---- | ------------------------------------ | -------------- | -------------------------- |
| MHA  | 每头一套 K、V                        | 无             | 缓存最大                   |
| GQA  | 每组 Q 头共享一套 KV                 | 份数（头数）   | 轻微质量损失               |
| MLA  | 不动头数，把 K、V 压成低秩潜向量存储 | **维度** | 低秩近似误差，质量基本不损 |

**核心机制：低秩联合压缩**

对当前 token 的隐藏状态 h_t，先压缩成一个低维"潜向量"，再上投影恢复 K、V：

```
c_t = W^DKV · h_t            潜向量，d_c << d_model
k_t = W^UK · c_t             恢复 key
v_t = W^UV · c_t             恢复 value
```

- **KV Cache 只缓存 c_t**（每 token 每层一份低维向量），不缓存恢复后的 K、V
- 压缩/恢复都是线性变换，恢复出的 K、V 参与标准注意力，数学上和直接算等价

**关键细节 ①：RoPE 必须单独解耦**

RoPE 要旋 Q、K。如果对从潜向量恢复出的完整 K 加 RoPE，旋转矩阵就"嵌进"了恢复路径，推理时无法做矩阵合并，只能缓存"加过 RoPE 的完整 K"——压缩立刻失效。解法：只对一小份独立的 key 做 RoPE：

```
k_t^R = RoPE(W^KR · h_t)      独立小份，维度 d^R 很小
```

于是每 token 缓存 = 潜向量 c_t（d_c 维）+ 小份 RoPE key（d^R 维）。

**关键细节 ②：权重吸收（推理时的矩阵合并）**

如果推理时每步先从 c_t 恢复出所有 K、V，虽然缓存省了、算力没省。MLA 把恢复矩阵"吸收"进 Q 和输出投影：

```
qᵀ k = qᵀ(W^UK c) = (W^UKᵀ q)ᵀ c        ← W^UK 吸收进 q，直接和潜向量点积
output = attn_weights @ (W^UV c)          ← 再吸收进输出投影
```

效果：推理时**既不缓存完整 K、V，也不显式恢复完整 K、V**——显存、算力一起省。

**数值（DeepSeek-V2）**

- d_c = 512，d^R = 64 → 每 token 每层只缓存 **576 维**
- 对比 MHA（64 头 × 128 维）每 token 每层需 2×64×128 = **16384 维**
- 减约 **93%**、约一个数量级 → 长上下文、大 batch 下显存带宽瓶颈大幅缓解

**和 MQA/GQA 的本质区别（面试加分点）**

- MQA/GQA 是**共享**：多个 Q 头共用同一组 K、V，靠牺牲表达力换缓存
- MLA 是**压缩存储**：每个头仍有自己完整的 K、V（从潜向量恢复），不牺牲头的独立性，质量基本不损
- 所以 MLA"省得更多 + 掉得更少"，代价是实现复杂（RoPE 解耦 + 权重吸收）

**面试答法**

> MLA 是 DeepSeek 提出的 KV Cache 压缩方案。GQA 通过减少 KV 头数量来省缓存，MLA 则不动头数，把 K、V 投影到低秩潜空间：每层只缓存一个低维潜向量，需要时再上投影恢复 K、V。它有两个关键细节：一是 RoPE 要单独解耦，只对一小份独立的 key 加旋转位置编码，否则旋转矩阵会卡住低秩压缩；二是推理时用权重吸收，把恢复矩阵合并进 Q 和输出投影，这样既不缓存也不显式恢复完整 K、V。最终每 token 每层只缓存 576 维，比 MHA 减约 93%。MLA 也是 DeepSeek-V2/V3 能低成本训练、支撑长上下文的关键。

### 5.9 面试要点

| 考点                               | 答案要点                                                                                      |
| ---------------------------------- | --------------------------------------------------------------------------------------------- |
| 为什么 Q 不需要缓存                | Q 只用于当前 token 查别人，历史 token 的 Q 对新 token 无意义                                  |
| 为什么 K 和 V 需要缓存             | K 供新 token 匹配，V 供加权聚合——两者都需要历史的完整信息                                   |
| KV Cache 在 Attention 公式里的位置 | 每次计算只有 Q 是维度 [1, d]，K 和 V 是 [历史长度, d]                                         |
| 瓶颈在哪                           | 显存带宽！不是计算量——每次生成一个新 token 都要把整个 KV Cache 从显存读一次，这是 I/O bound |
| Prefill 和 Decode 的区别           | Prefill 计算密集（大矩阵乘），Decode 访存密集（串行 + 反复读 KV Cache）                       |
| 投机解码怎么加速                   | 小模型草稿 + 大模型并行验证：把 N 次访存密集串行 decode 换成 1 次计算密集大矩阵乘（见 5.7）   |
| MLA 为什么省显存                   | 把 K、V 压缩成低秩潜变量（RoPE 单独解耦），Cache 减 ~93%，DeepSeek-V2/V3 核心                 |

## 六、RoPE（旋转位置编码）与长上下文

### 6.1 为什么需要 RoPE：三类位置编码的演进

| 类型                        | 代表                                        | 做法                       | 缺点                                   |
| --------------------------- | ------------------------------------------- | -------------------------- | -------------------------------------- |
| **绝对位置编码**      | Transformer 正弦、BERT 可学习               | 位置信息加到 embedding 上  | 模型难以直接利用"相对距离"；长度外推差 |
| **相对位置编码**      | T5 bias、ALiBi、DeBERTa                     | 注意力打分时按相对距离调整 | 需要改注意力实现；表达能力/泛化受限    |
| **旋转位置编码 RoPE** | LLaMA、Mistral、Qwen、DeepSeek、PaLM、Gemma | 把位置"旋转"进 Q、K        | 直接外推仍有限制（需要缩放，见 6.4）   |

核心矛盾：注意力的本质是**相对位置**敏感的——"我打你"和"你打我"的区别在于词之间的相对顺序，而不是绝对序号。绝对位置编码只给了"我在第几位"，模型很难直接学到"我们俩隔多远"；RoPE 直接把相对距离编码进注意力内积。

### 6.2 数学原理（面试常考）

对第 i 对维度 (2i, 2i+1)，频率与 Transformer 正弦编码同款：

```
ω_i = 1 / 10000^(2i/d)，i = 0, 1, ..., d/2 - 1
```

位置 m 的旋转矩阵是块对角矩阵，每个块是二维旋转：

```
R_i(m) = [ cos(m·ω_i)   -sin(m·ω_i) ]
         [ sin(m·ω_i)    cos(m·ω_i) ]

q_m = R(m)·q      （把位置 m 旋转进 Query）
k_n = R(n)·k      （把位置 n 旋转进 Key）
```

**关键恒等式**（面试必答）：

```
q_mᵀ k_n = (R(m)q)ᵀ(R(n)k) = qᵀ R(m)ᵀ R(n) k = qᵀ R(n−m) k
```

推导依赖两条性质：

1. 旋转矩阵**正交**：RᵀR = I，旋转不改变向量长度（内积大小只由夹角决定）
2. 角度**可加**：R(m)ᵀR(n) = R(n−m)（先反向旋转 m、再正向旋转 n，等价于直接旋转差值）

结论：**Q、K 都旋转后，内积只与相对位置 n−m 有关**，与绝对位置无关——模型天然学会相对位置。

直观理解：把每个 token 的向量按位置"拧"一个角度，两个向量的夹角差 = 位置差 × 频率。高频维度（i 小）转得快，负责捕捉近处细节；低频维度（i 大）转得慢，负责长程一致。

另一个性质是**相对衰减（relative decay）**：对固定的 query，与远处 key 的内积上界随距离增大而衰减——天然符合"越近越相关"的归纳偏置。

### 6.3 为什么主流模型都选 RoPE

1. **相对位置性**：内积只依赖相对距离，符合注意力语义
2. **外推性相对好**：位置以"连续角度"形式存在，而不是离散 embedding 查表，超长度时行为更可预测
3. **零参数、零推理开销**：cos/sin 表预计算；旋转可以和 Q/K 投影权重合并（先算 q = W_q x，再旋转），不增加计算量
4. **兼容性好**：和 GQA、MLA（DeepSeek）、线性注意力等优化都能共存
5. **长上下文扩展手段成熟**（见 6.4）

注意：RoPE **不是开箱即用的无限外推**——超过训练长度照样崩，原因见下。

### 6.4 如何把上下文从 4K 扩到 128K

| 方法                                   | 做法                                                                                               | 特点                                                                                                |
| -------------------------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **直接外推**                     | 位置直接超过训练长度                                                                               | ❌ 高频维度旋转角度超出训练时见过的范围，注意力错乱                                                 |
| **Position Interpolation（PI）** | 位置统一除以缩放比 s（等价于把角度压回训练范围）                                                   | ✅ 平滑稳定，但相邻位置角度差变小（分辨率下降）；需要几千步继续训练。LLaMA 2 的 4K→32K 用的就是 PI |
| **NTK-aware 缩放**               | 提高 RoPE base（10000 → 更大），高频维度几乎不动、低频维度被压缩                                  | 零训练也能凑合，但效果有限                                                                          |
| **YaRN（NTK-by-parts + 温度）**  | 按频率分三段：高频不缩放（保细节）、中间插值、低频均匀缩放；再加 attention 温度（context scaling） | 目前最常用。DeepSeek-V2 用它 4K→128K**只训练 1000 步**                                       |
| **分阶段继续预训练**             | 短窗口训练 → 逐步拉长 + 混入长文本数据；同时提高 RoPE base 频率（如 500K）                        | LLaMA 3.1：预训练 8K → 继续预训练扩展到 128K                                                       |
| **滑窗 / 分段注意力**            | 不改位置编码，只限制注意力范围                                                                     | 治标不治本，远距离信息访问受限                                                                      |

**面试高频追问：直接外推为什么崩？**
因为高频维度（i 小）的旋转角速度大，训练时只见过角度在 [0, L·ω_i] 范围内的相位分布；测试时位置超过 L，相位进入模型"没见过"的区域，相当于分布外输入。插值（PI）则把所有角度**压缩回训练见过的范围**，所以有效，代价是高频分辨率下降（相邻位置区分度变低）。

### 6.5 长上下文 ≠ 用得好长上下文

- **Lost in the Middle（Liu et al., 2023）**：信息放在上下文**中间**最容易被模型忽略，开头和结尾记得最牢——长上下文窗口变长后这个问题更严重
- 长上下文评测的陷阱：单点检索（needle-in-a-haystack，在长文本里找一个句子）通过 ≠ 多跳推理、长程依赖、跨段落规划通过
- 工程对策：关键信息尽量放前/后、用检索（RAG）把最相关内容提到前面、让模型先定位再回答

### 6.6 面试要点

| 考点                        | 答案要点                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| RoPE 的相对位置从哪来       | 旋转矩阵正交 + 角度可加：qᵀR(m)ᵀR(n)k = qᵀR(n−m)k，内积只依赖相对距离                  |
| 为什么只旋转 Q、K，不旋转 V | V 不参与"匹配"，只提供被聚合的内容                                                         |
| 为什么 LLaMA/GPT 都用 RoPE  | 相对位置性质、零参数、无推理开销、长上下文扩展手段成熟                                     |
| RoPE 和 ALiBi 的区别        | ALiBi 在注意力分数上直接加线性 bias（距离越远惩罚越大）；RoPE 通过旋转内积隐式编码相对位置 |
| 直接外推为什么崩            | 高频维度相位分布超出训练范围（分布外）                                                     |
| PI 的代价                   | 相邻位置角度差变小，位置分辨率下降                                                         |
| 主流长上下文方案            | 提高 RoPE base + 高质量长文继续预训练 + YaRN/PI 缩放                                       |

## 七、现代预训练技术

### 7.1 数据工程：预训练的天花板

**数据质量决定模型上限**，架构和算力只是把数据里的规律学出来。

| 环节                              | 做法                                                                 | 说明                                                                                                                                  |
| --------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **清洗过滤**                | 启发式规则（长度、重复率、困惑度）+ 分类器打分（fastText/质量模型）  | 网页噪音极多，低质数据会拖垮下游能力                                                                                                  |
| **去重**                    | 文档级 MinHash 去重、跨语言去重                                      | 重复数据导致记忆过拟合、训练浪费                                                                                                      |
| **去污（decontamination）** | 从训练集剔除与评测集重叠的文本（模糊匹配 + 人工抽查）                | 防止"背答案"式的假高分，评测才有意义                                                                                                  |
| **数据配比**                | 网页/书籍/代码/数学/多语言按比例混合                                 | 配比直接决定能力结构：代码占比高 → 推理与结构化能力强（LLaMA-1 约 67% 英文网页、15% 非英文、4.5% 书籍、4.5% 维基、4.5% 代码 + 学术） |
| **数据退火（annealing）**   | 训练最后 10-20% 换成精选高质量数据                                   | 成本极低、涨点明显（Qwen、Nemotron 都这么做）                                                                                         |
| **合成数据**                | 用强模型生成数学、代码、逻辑数据补进预训练                           | Phi 系列几乎全靠合成数据；能补足网上稀缺的高质量推理数据                                                                              |
| **打包与文档掩码**          | 多个文档用`<eos>` 连接打包成固定长度序列；注意力掩码阻止跨文档关注 | 防止模型学到"文档之间有关联"的伪信号                                                                                                  |
| **Tokenizer**               | BPE/SentencePiece；词表 32K~150K                                     | 代码要处理好缩进空格与数字切分                                                                                                        |

> **记忆框架（8 环节速记："选—配—喂"）**：① 选（质量三连）：清洗过滤（规则+分类器打分）、去重（MinHash）、去污（剔除评测重叠防背答案）；② 配（结构三件）：数据配比（配比决定能力结构）、数据退火（最后 10-20% 换精选高质量）、合成数据（强模型补推理数据）；③ 喂（工程两件）：打包+文档掩码（`<eos>` 连接防跨文档伪信号）、Tokenizer（BPE，32K~150K）。

### 7.2 Scaling Laws：训多大、训多少数据

| 结论                                                                  | 来源                               | 含义                                                                                |
| --------------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------- |
| 模型越大越好（算力受限时代）                                          | Kaplan et al. 2020                 | 当时数据相对充裕，提升参数最划算                                                    |
| **计算最优**：参数与数据同步增长，约 **20 tokens / 参数** | Chinchilla（Hoffmann et al. 2022） | 70B 模型配 ~1.4T tokens；70B 再堆数据不如把预算分给更大模型                         |
| 实际趋势：**数据远超 Chinchilla 最优**                          | LLaMA-3 8B 用了 15T tokens         | 因为部署成本约束下"小模型 + 海量数据"推理更便宜，而且多训数据在推理任务上仍持续涨点 |

**面试常问：为什么现在大家都在堆数据而不是堆参数？**
两个原因：一是 Chinchilla 之后大家认识到数据和参数要平衡；二是推理/部署成本约束——同样效果下小模型便宜得多，所以宁可让 8B 模型吃 15T tokens 也不做 70B。

### 7.3 优化与训练稳定性

- **优化器**：AdamW + 权重衰减（0.1）+ β2 ≈ 0.95
- **学习率调度**：线性 warmup（约 1-2K 步）→ cosine 衰减到峰值的 10%
- **梯度裁剪**：global norm ≈ 1.0，防止单 batch 异常炸掉训练
- **混合精度 BF16**：FP16 尾数只有 10 位，梯度/激活容易溢出；BF16 指数范围与 FP32 相同，训练更稳（LLaMA 全系）
- **Loss spike（损失尖峰）**：训练中损失突然跳高，常见原因是数据批次问题或学习率异常。LLaMA 3 的实战经验：**发现 spike 就回滚到 spike 之前的 checkpoint，并定位触发 batch 检查数据**
- **并行策略**：
  - 数据并行（ZeRO / FSDP）：每卡一份模型，梯度通信；显存与通信权衡
  - 张量并行：单层内切分权重（跨卡）
  - 流水线并行：按层切分（跨卡串行）
  - 序列并行：长序列时切分序列维度
  - MoE 还要**专家并行**（token 路由到不同卡上的专家，all-to-all 通信）
- **工程保障**：定期 checkpoint + 自动恢复、loss/梯度范数监控、吞吐与显存日志

> **记忆框架（训练稳定五件套："优-调-剪-混-尖"）**：优化器（AdamW + 权重衰减 0.1 + β2≈0.95）→ 学习率调度（线性 warmup 1-2K 步 → cosine 衰减到 10%）→ 梯度裁剪（norm≈1.0）→ 混合精度 BF16（FP16 尾数 10 位易溢出，BF16 指数同 FP32 更稳）→ Loss spike 处理（回滚 + 查 batch）。**并行五类（"数-张-流-序-专"）**：数据并行（ZeRO/FSDP 切分参数/梯度/优化器状态）、张量并行（层内切权重，通信大）、流水线并行（按层切，有气泡）、序列并行（切序列维度）、专家并行（MoE 路由，all-to-all）。

### 7.4 架构级新实践（现代 LLM 的"标配"）

| 技术                                         | 内容                                             | 收益                                                                                                   |
| -------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **Pre-Norm + RMSNorm**                 | 归一化移到子层之前；RMSNorm 去掉均值计算         | 训练稳定（pre-norm 梯度更干净）；省 ~30% 归一化开销。LLaMA 全系标配                                    |
| **SwiGLU 激活**                        | 门控线性单元（FFN hidden 缩为 2/3）              | 比 GELU/ReLU 效果更好（LLaMA 采用）                                                                    |
| **GQA**（Grouped Query Attention）     | 多个 Q 头共享一组 KV 头                          | KV Cache 减到 1/8 量级，推理快、显存省（LLaMA 2 70B、Mistral 起）                                      |
| **去掉 bias**                          | 所有线性层无 bias                                | 省参数、省激活显存、训练更稳（LLaMA 细节）                                                             |
| **MLA**（Multi-head Latent Attention） | 把 KV 压缩成低秩潜变量，RoPE 单独解耦处理        | KV Cache 减 ~93%，DeepSeek-V2/V3 的核心省显存手段（详见 5.8）                                          |
| **MoE**（Mixture of Experts）          | 门控路由：每个 token 只激活部分专家              | 总参数大、单次激活小：DeepSeek-V3 共 671B、每 token 只激活 37B；代价是路由不均衡、通信开销、显存装载难 |
| **混合 SSM 架构**                      | Mamba/线性注意力层与注意力层交替（Jamba、Zamba） | 长序列计算 O(n)，缓解 KV Cache 与注意力平方复杂度                                                      |

**MoE 补充细节（DeepSeek-V3 为代表）**：

- 细粒度专家（把大专家切成多个小专家）+ 共享专家（所有 token 都过）
- 负载均衡：无辅助损失策略 + 补丁 bias 调节，避免"部分专家饿死"
- 训练成本：约 14.8T tokens，约 280 万 H800 GPU 小时——比同规模稠密模型便宜一个量级

> 这些机制如何组合起来"引爆"行业（DeepSeek 复盘 + 其他前沿模型的独特机制），见 **第十四章**。

### 7.5 预训练的阶段性设计（staged pretraining）

现代预训练不是"一种数据训到底"，而是分阶段课程式推进：

```
阶段 1：通用语料学语言（网页、书籍、多语言）→ 基础语言能力
阶段 2：高质量推理数据增强（代码、数学、科学）→ 推理与结构化能力
阶段 3：长上下文延伸（8K → 128K，如 LLaMA 3.1：调 RoPE base + 长文本继续预训练）
阶段 4：数据退火（最后 10% 用精选高质量数据）
```

**领域继续预训练（continued pretraining / mid-training）**：在通用预训练之后、SFT 之前，用领域语料（代码、法律、医疗、金融）继续训练。

- 作用：注入**领域知识**（长尾事实、术语、格式、代码库风格）
- 注意：必须混入通用数据防止**灾难性遗忘**（只学领域会把通用能力洗掉）
- 与 SFT 的分工：**继续预训练注入"知识"，SFT 注入"行为"**——知识学不进 SFT（数据量太小），行为改不了预训练（目标不对）

## 八、后训练：SFT 与对齐（RLHF / DPO / GRPO）

### 8.1 后训练要解决什么

预训练产出的只是"续写机器"：会预测下一个 token，但不会问答、不会拒绝、风格不友好、不会遵循指令。

```
预训练（学知识、学语言）
   ↓
SFT（学格式与行为：会对话、会听指令）
   ↓
偏好对齐（学好坏：RLHF / DPO / GRPO，说人话、不胡说、不做坏事）
   ↓
能力特化（工具调用、长上下文、代码、推理——见第九、六章）
   ↓
推理时：RAG、约束解码、test-time scaling
```

一句话总结：**预训练学"知识"，SFT 学"格式与行为"，RL 学"偏好与目标"**。

### 8.2 SFT：让模型学会听指令

- **数据**：指令-回复对，来源 = 人工编写 + LLM 合成 + 真实对话提取
- **质量 > 数量**：LIMA 实验用 1000 条精选数据就达到显著对齐效果（"Less Is More for Alignment"）
- **格式设计**：chat template（system/user/assistant 角色）、特殊 token（如 `<|im_start|>`）；**训练时用因果掩码，loss 只计算 assistant 部分的 token（masked SFT）**——模型只学"怎么回答"，不学"怎么提问"
- **数据配比**：通用对话 + 专项能力（代码、数学、工具）混合，防止能力失衡和灾难性遗忘
- **常见误区**：SFT 不能注入新知识（见 7.6）；知识型问题要靠 RAG 或预训练数据

### 8.3 RLHF（PPO 路线）：经典但重

```
SFT 模型
 ├─ 作为参考模型 π_ref（冻结）
 └─ 作为初始策略 π_θ
奖励模型 RM：人类给同一 prompt 的多个回答排序 → Bradley-Terry 二分类 → 学会"哪个更好"
PPO 循环：π_θ 采样回答 → RM 打分 → critic 提供每步基线 → 策略更新（重要性采样 + clip + GAE advantage）
         critic 也用实际回报同步训练（回归）
损失里带 KL 惩罚：KL(π_θ || π_ref) 防止跑飞
```

目标函数（简化）：

```
max E[r(x, y)] - β·KL[π_θ(y|x) || π_ref(y|x)]
```

- **为什么需要 KL 约束**：RM 是对人类偏好的有损近似，模型可以"刷分"（reward hacking，比如输出越来越长、越来越谄媚）；KL 把策略钉在参考模型附近，保证语言流畅不退化
- **为什么 PPO**：on-policy，在线采样，能看到自己当前分布下的样本；比 off-policy 稳定
- **缺点**：工程复杂（策略 + 参考 + RM + critic 四份模型）、显存大、训练不稳定、调参成本高

### 8.3.1 KL 散度（Kullback-Leibler Divergence）：公式与直觉

KL 散度衡量两个概率分布 P 和 Q 的差异——准确说是"**用 Q 去近似 P 时，平均损失多少信息量**"。它是 RLHF/DPO/GRPO 里所有 KL 惩罚项的数学基础。

**公式（离散形式）**：

```
KL(P || Q) = Σ_x P(x) · log( P(x) / Q(x) )
           = Σ_x P(x) · [ log P(x) - log Q(x) ]
```

**连续形式**：

```
KL(P || Q) = ∫ p(x) · log( p(x) / q(x) ) dx
```

**为什么要 log 的比值（信息论直觉）**：log(1/P(x)) 是"事件 x 携带的信息量"（单位 nat 或 bit）。如果**错误地**假设真实分布是 Q，那么同一个事件 x 会被编码成 log(1/Q(x)) 个 bit。两者之差 log(1/Q) - log(1/P) = log(P/Q)，就是"因为这个错误假设，每条消息平均多付的 bit 数"。对 x 按 P 加权平均，得到的就是 KL——所以 KL 的直观含义是"**用错误的分布近似真实分布时，平均多付出的编码代价**"。

**三个关键性质（面试必答）**：

1. **KL ≥ 0，当且仅当 P = Q 时等于 0**（Gibbs 不等式，由 Jensen 不等式推出：log 是凹函数，E[log(P/Q)] ≤ log E[P/Q] = log 1 = 0，取负号即 KL ≥ 0）。注意需要满足绝对连续性：P 不为 0 的地方，Q 也不能为 0（否则 log(P/0) 发散）。
2. **不对称**：KL(P‖Q) ≠ KL(Q‖P)。方向不同含义不同——"用 Q 近似 P 的损失"和"用 P 近似 Q 的损失"不是一回事。因此它**不是**真正的距离度量（不满足对称性，也不满足三角不等式）。
3. **和交叉熵、熵的关系**：`KL(P‖Q) = H(P, Q) - H(P)`，其中 H(P,Q) = -Σ P(x) log Q(x) 是交叉熵，H(P) = -Σ P(x) log P(x) 是熵。训练时 P 通常是数据分布（固定），H(P) 是常数，所以**最小化 KL = 最小化交叉熵 = 最大似然**。这解释了为什么语言建模里用交叉熵损失，本质上就是在做"最小化模型分布和数据分布的 KL"。

**数值例子（亲手验证性质）**：

设 P = [0.5, 0.5]，Q = [0.9, 0.1]，用自然对数（单位 nat）：

```
KL(P||Q) = 0.5·log(0.5/0.9) + 0.5·log(0.5/0.1)
         = 0.5·(-0.588) + 0.5·(1.609) = 0.511

KL(Q||P) = 0.9·log(0.9/0.5) + 0.1·log(0.1/0.5)
         = 0.9·(0.588) + 0.1·(-1.609) = 0.368
```

两个方向的值不同（0.511 vs 0.368），且都 > 0——不对称性和非负性一眼可见。

**RLHF 里的 KL 惩罚具体长什么样**：

PPO 目标函数里那一项，展开写是：

```
KL(π_θ || π_ref) = E_{x~数据, y~π_θ}[ log( π_θ(y|x) / π_ref(y|x) ) ]
```

逐 token 计算（token 级别平均）：

```
KL ≈ (1/T) · Σ_t log( π_θ(y_t | x, y_<t) / π_ref(y_t | x, y_<t) )
```

注意期望是对**当前策略 π_θ 采样**的——每个 token 都把"新策略给出这个 token 的概率"和"参考模型给出这个 token 的概率"取对数比、求和。策略每偏离参考模型一点，就付一点代价。β 是惩罚强度超参。

**为什么用 KL 而不是别的度量**：

- 方向不对称正好用对：KL(π_θ‖π_ref) 惩罚"当前策略在参考模型认为大概率的地方给出小概率"——也就是策略去钻 RM 空子（reward hacking）时，偏离 π_ref 必然变大，被惩罚；
- 逐 token 可加、可微，天然适配语言模型的训练框架；
- π_ref 是 SFT 模型，KL 惩罚的直觉就是"**不要离正常说话的模型太远**"。

### 8.3.2 策略梯度定理：从零推导（面试重灾区）

**目标**：最大化期望奖励

```
J(θ) = E_{y~π_θ}[ r(x, y) ] = ∫ π_θ(y|x) · r(x,y) dy
```

**第 1 步：梯度搬进积分**

```
∇J(θ) = ∫ ∇π_θ(y|x) · r(x,y) dy
```

为什么合法：r(x,y) 是 RM 打分，**不含 θ**（梯度为 0 不动）；积分限是对 y 积分，也不含 θ。

**第 2 步：log 导数技巧（链式法则移项）**

```
∇log π_θ(y|x) = ∇π_θ(y|x) / π_θ(y|x)   ⇒   ∇π_θ(y|x) = π_θ(y|x) · ∇log π_θ(y|x)
```

代入：

```
∇J(θ) = ∫ π_θ(y|x) · [∇log π_θ(y|x)] · r(x,y) dy
```

**第 3 步：认出期望，转为采样**

这个积分是"函数 `∇log π_θ·r` 在分布 π_θ 下的期望"的标准形式：

```
∇J(θ) = E_{y~π_θ}[ ∇log π_θ(y|x) · r(x,y) ]
        ≈ (1/N) · Σ_i ∇log π_θ(y_i|x) · r(x,y_i)      ← 蒙特卡洛采样
```

`∇log π_θ(y_i|x)` 恰好是反向传播能直接算的量（模型输出 log 概率对参数的梯度），所以"梯度"从不可采样的神秘量变成了可采样的量。

**为什么必须 log（为什么不能直接用 `∇π_θ·r` 采样）**：

`∫ ∇π_θ(y)·r(y) dy` **不是期望形式**——被积函数里没有密度权重 π_θ 站在乘法的位置上（∇π 是密度的梯度，密度"藏在导数里面"）。直接采样 y~π_θ 求平均，估计量的期望会带出一个多余的 π_θ(y)：

```
E_{y~π_θ}[∇π_θ(y)·r(y)] = ∫ ∇π_θ(y)·r(y)·π_θ(y) dy ≠ ∫ ∇π_θ(y)·r(y) dy     ← 有偏
```

用**重要性采样**修：任意积分都能改写成期望 `∫ g(y)dy = ∫ [g(y)/q(y)]·q(y)dy = E_{y~q}[g(y)/q(y)]`。取 q=π_θ、g=∇π·r：

```
∇J = E_{y~π_θ}[ ∇π_θ(y)·r(y) / π_θ(y) ] = E_{y~π_θ}[ r(y) · ∇log π_θ(y) ]
```

"除以密度"这步**自动导出了 log**——所以 log 导数技巧不是拍脑袋的 trick，而是"采样后除以密度"的必然结果。工程上还必须用 log 形式：连续空间的密度（归一化常数）不可解，而 ∇logπ 直接来自策略网络、数值也更稳定。

**第 4 步：加基线（advantage）——解决方差大**

奖励全为正（RM 打分 0~5）时，所有样本概率都会上升，只是好样本升得多，梯度方差大。减去基线 b（"这个 prompt 大概得多少分"的估计）：

```
A(x,y) = r(x,y) - b      ⇒   ∇J ≈ (1/N) Σ ∇log π_θ(y_i)·A(x,y_i)
```

A>0 的样本概率升、A<0 的样本概率降——正负分明，方差大降。**基线 b 从哪来，就是 PPO（critic）与 GRPO（组内均值）的分水岭**。

### 8.3.3 PPO 完整目标与 critic：TD 误差与 GAE（数值例子）

**critic 的角色**：PPO 的奖励和优势是**逐 token** 的（一个长回答里每个 token 都要算 advantage），所以基线 b 必须是"**每个状态的价值**"——这就是 critic V(s) 存在的理由。critic 和策略在 RL 阶段**同步训练**（回归到实际回报），是一个完整可训练模型（参数 + 梯度 + 优化器状态），所以 PPO 显存翻倍。注意 **critic ≠ RM**：RM 是 RL 前训好、冻结的打分器；critic 是 RL 阶段边用边训的价值网络。

**完整循环**：

```
for 每次迭代:
  1. 用 π_old 采样一批轨迹（逐 token 生成）
  2. RM 给最终回答打标量分 r
  3. 把奖励按 TD 回传给每个 token，算 advantage：
       δ_t = r_{t+1} + γ·V(s_{t+1}) - V(s_t)        ← TD 误差（需要 critic 预测）
       A_t = Σ_l (γλ)^l · δ_{t+l}                    ← GAE 指数加权累积
  4. 更新策略：L = E[ min(ρ·A, clip(ρ, 1±ε)·A) ]   ← 用第 3 步的 A
  5. 更新 critic：损失 = Σ (V(s_t) - G_t)²          ← G_t 为实际累计回报，让估值更准
  6. π_old ← π_θ，重新采样
```

> **π_θ 的梯度在哪算（伪代码第 4 步展开）**：角色——π_θ 是当前优化的新策略（θ 是自由变量），π_old 是采样时的旧快照（冻结，直到第 6 步才更新），A_t 是常数（来自 critic/RM，不回传）。梯度形式：`∇θ L = Σ_t ∇θ log π_θ(a_t|s_t)·A_t·[clip 有效区]`——只有 π_θ 的 log 概率对 θ 求导（策略梯度定理的 log 技巧，见 8.3.2）。clip 在 ρ 超出 [1±ε] 时把梯度置 0 = **切断极端梯度**。更新动作：`θ ← θ + Adam(∇θ L)`（梯度上升）。critic 更新是**另一套参数、另一条梯度链**，同一 batch 交替更新。

> **为什么是梯度上升而不是梯度下降**：RL 目标是**最大化期望奖励** max E[r]，和监督学习"最小化误差"方向相反。`L=min(ρA, clip(ρ)A)` 最大化后：A>0 的轨迹 ρ 被推大（升概率）、A<0 的轨迹 ρ 被压小（降概率）——正好实现"好回答升、坏回答降"。A 是"动作相对平均有多好"（权重/坡度），ρ 是"概率该不该调"（方向），clip 是"每步最多走多远"（步长限制）。不能无限推大 ρ：clip 切梯度 + RLHF 的 KL 惩罚，是**受约束的最大化**。

**数值例子**（把每一步算出来）：

设模型生成了一条 4-token 的回答，γ=0.9，λ=0.95（GAE），RM 在回答末尾一次性给奖励 1.0：

```
s0 --t1--> s1 --t2--> s2 --t3--> s3 --t4--> s4（结束）
r1=0        r2=0        r3=0        r4=1.0
```

critic 当前的预测（每步基线）：

```
V(s0)=0.5  V(s1)=0.6  V(s2)=0.7  V(s3)=0.8  V(s4)=0（终止态）
```

**第 1 步：算 TD 误差** `δ_t = r_{t+1} + γ·V(s_{t+1}) - V(s_t)`：

```
δ1 = 0 + 0.9×0.7 - 0.6 = 0.03
δ2 = 0 + 0.9×0.8 - 0.7 = 0.02
δ3 = 1.0 + 0.9×0   - 0.8 = 0.20
```

**第 2 步：算 GAE advantage** `A_t = δ_t + γλ·δ_{t+1} + (γλ)²·δ_{t+2} + ...`，γλ = 0.9×0.95 = 0.855：

```
A1 = 0.03 + 0.855×0.02 + 0.855²×0.20 = 0.03 + 0.017 + 0.146 = 0.193
A2 = 0.02 + 0.855×0.20 = 0.191
A3 = 0.20
A4 = 0（终止态）
```

（注意 λ 的取舍：λ→1 时 GAE 看完整轨迹、偏差小方差大；λ→0 时只看当前步、方差小偏差大。λ=0.95 是常用折中。）

> **GAE vs 单步 TD（面试追问：为什么 GAE 更好）**：单步 TD 只是 GAE 的特例（λ=0）。GAE 三大优势：
>
> 1. **降低偏差（少依赖 V 自举）**——累积多步真实奖励，V 估计不准时更鲁棒；
> 2. **可调偏差-方差**——λ 把"纯单步（偏差大方差小）→ 纯 MC（无偏方差大）"连成连续谱，取最优点；
> 3. **平滑噪声 + 更好信用分配**——多步加权平均=平滑，稀疏/延迟奖励下每步都有平滑信号。
>    数值例：δ1=0.03、δ2=0.02、δ3=0.20（奖励在结尾），单步 A1=0.03（几乎无信号），GAE A1=0.03+0.855×0.02+0.855²×0.20=0.193（看到后续奖励贡献）。

**第 3 步：用 A 更新策略**。每个 token 用自己的 A_t 进 PPO 的 clip 目标——A>0 的 token 概率被强化、A<0 的削弱，clip 限制单步幅度。最终回答结尾的 token（A3=0.20）得到的强化信号最强，因为奖励在结尾。

**第 4 步：更新 critic**。用每个状态的实际累计回报 G_t 做回归：

```
G1 = 0 + 0.9×0 + 0.9²×1.0 = 0.81
G2 = 0 + 0.9×1.0 = 0.90
G3 = 1.0
G4 = 0（终止态）

critic 损失 = (0.6-0.81)² + (0.7-0.90)² + (0.8-1.0)² + (0-0)² = 0.124
```

下一轮 critic 会预测得更高一些，advantage 相应变化——critic 与策略互相迭代推进。

> **关于"真实 G_t"的关键澄清（面试追问）**：
>
> 上面用的 G_t 是 **MC 回报**——把轨迹里环境真实给的奖励按 γ 折现累加（本例即"结尾 RM 分回传"），只依赖真实奖励、不依赖 critic。但有三点要清楚：
>
> 1. **单次采样的 G_t 是"有噪声的样本"，不是真值**。真正的期望回报 V*(s_t)=E[G_t] 需要无数次采样平均；一次轨迹给的是无偏但高方差的估计。
> 2. **实际 PPO 的 critic 目标通常不是纯 MC**，而是 GAE/TD 目标：`G_t = A_t + V(s_t)`。展开后含 `γ·V(s_{t+1})`，即 **critic 自己的预测**。所以目标是"一半真实（r 部分）+ 一半自举（V 部分）"。
> 3. 正因如此 critic 是 **TD 自我 bootstrap**：目标里含自己的预测，所以 critic 必须和策略交替训练、互相校准。
>
> 一句话：**真实奖励只有 r 那一份，后半段的"未来价值"是 critic 自己猜的。**

**PPO vs GRPO 的基线来源（衔接 8.5）**：PPO 需要 critic 是因为奖励/优势逐 token、需要"每步状态价值"；GRPO 的奖励是**整条回答级别**（对了=1、错了=0），同一 prompt 采 G 条做**组内对比**当基线，于是不需要逐状态估值，critic 整个省掉。

> **PPO 三件套速记（面试"每件解决什么问题"必答）**：
>
> - **重要性采样 → 解决旧数据复用**：PPO 理论上是 on-policy，每次更新后旧数据"过期"。用概率比 ρ=π_θ/π_old 修正分布偏差（E_πθ[f]=E_πold[f·ρ]），就能用旧策略采的数据更新新策略。**clip 截断的就是这个 ρ**。
> - **clip → 解决步子过大**：`min(ρA, clip(ρ,1±ε)A)`，把概率比限制在 [1-ε, 1+ε]，切断极端梯度、防止单次更新策略跳太远。
> - **GAE → 解决稀疏奖励回传 + 偏差方差权衡**：RM 只在回答结尾给分，需回传给每个 token。纯 TD（δ_t=r+γV(s')-V(s)）偏差大方差小；纯 MC 无偏但方差大。GAE 按 (γλ)^l 加权累加 TD 误差，λ=0 即纯 TD、λ=1 即纯 MC，λ 调平衡。
> - **critic vs RM（常考）**：critic = RL 阶段**边用边训**的价值网络 V(s)，提供逐 token 基线、是 PPO 显存翻倍的来源；RM = RL 前**训好冻结**的裁判。记忆锚点：RM=标准（裁判），critic=优化工具（基线）。
> - **一句话**：ρ 管"数据能用"，clip 管"步子多大"，GAE 管"奖励怎么分"。

### 8.4 DPO 与"无奖励模型"派系

**核心洞察**：RLHF 的最优策略有闭式解 π* ∝ π_ref·exp(r/β)，把它代回 Bradley-Terry 偏好概率，奖励模型 r 可以被**消掉**——直接用偏好对训练策略：

```
L_DPO = -log σ( β·log(π_θ(y_w)/π_ref(y_w)) - β·log(π_θ(y_l)/π_ref(y_l)) )
```

直觉：让"被人类选中的回答 y_w 的概率相对参考模型**提升**"，让"被拒绝的回答 y_l 的相对概率**下降**"。

|            | RLHF（PPO）          | DPO                        |
| ---------- | -------------------- | -------------------------- |
| 奖励模型   | 需要训练 RM          | 不需要（隐式奖励）         |
| 采样       | 在线 RL（on-policy） | 静态偏好数据（offline）    |
| 工程复杂度 | 高（4 个模型）       | 低（一个模型 + 参考）      |
| 稳定性     | 差（超参敏感）       | 好                         |
| 短板       | 贵、不稳定           | 无探索；对偏好数据质量敏感 |

**DPO 变体**（面试展示广度用）：

- **IPO**：把 KL 正则直接写进损失，超参更稳
- **KTO**：不需要成对数据，只要"好/坏"标签
- **ORPO**：SFT 和偏好优化一步完成（训练中同时区分好答案）
- **SimPO**：去掉参考模型，用输出长度归一化的隐式奖励
- **R-DPO**：修正 DPO 对"长答案"的偏差

### 8.5 GRPO 与可验证奖励（DeepSeek-R1 路线，当下最热）

> 这两个技术回答的是**两个正交的问题**：**GRPO 管"用什么算法优化"（怎么更新策略），RLVR 管"奖励从哪来"（怎么打分）**。一个管方法、一个管信号来源，合起来才是推理模型（o1/R1）能跑起来的完整拼图。

#### 8.5.1 GRPO：Group Relative Policy Optimization

**PPO 的痛点**：PPO 为了给**每一个 token** 算 advantage，需要"每个状态的价值"做基线——这就是 critic（价值网络），和策略一样大，且是 RL 阶段**边用边训练**的完整模型（参数 + 梯度 + 优化器状态），显存直接翻倍。

**GRPO 的关键观察**：奖励其实是**整条回答级别**的（答案对了=1、错了=0），根本不需要给中间每个 token 单独估价值。于是思路变成——**不估每步价值，对同一 prompt 采 G 条回答，用"组内相对好坏"当 advantage**：

```
1. 对 prompt x，采样 G 条回答 y1...yG（一组）
2. 打分 r1...rG（来自 RLVR 规则，或冻结的 RM）
3. 组内归一化：A_i = (r_i - mean(r)) / std(r)
4. 策略梯度更新：∇J = E[ A_i · ∇log π_θ(y_i) ]
5. 带 KL 约束（防偏离 π_ref）
```

**为什么"组内相对"就够：数字例子**。prompt：`解方程 2x+3=7`，G=4 条回答，规则奖励：

| 回答 | 内容                            | r | A=(r-mean)/std |
| ---- | ------------------------------- | - | -------------- |
| y1   | "x=2"（对）                     | 1 | +1             |
| y2   | "x=3"（错）                     | 0 | -1             |
| y3   | "x=2，7-3=4，4/2=2"（对且详细） | 1 | +1             |
| y4   | "x=5"（错）                     | 0 | -1             |

（mean=0.5, std=0.5）两条正确回答都被强化、两条错误都被削弱，模型同时学到"简洁正确"和"详细正确"两种答法。即使某组全错（题目很难），组内归一化也让"相对没那么错"的那条拿到正 advantage——**模型始终有方向可学**。

**PPO vs GRPO 对比**：

|          | PPO                                 | GRPO                                           |
| -------- | ----------------------------------- | ---------------------------------------------- |
| 基线来源 | critic 逐状态估计 V(s)              | 组内 G 条回答的均值/标准差                     |
| 显存     | 策略+critic 双训练模型，翻倍        | 省掉 critic（及其梯度+优化器状态），省一半以上 |
| 算力     | critic 的训练（反向传播，串行迭代） | 采样 G 条回答（前向推理，可并行）              |
| 代价     | critic 训练昂贵                     | 推理成本 ×G                                   |

**为什么"前向 ×G"比"训练 critic"便宜**：前向推理没有反向传播和优化器状态的显存/算力，且 G 条回答可以**并行**生成；critic 则要串行训练多轮才收敛。用便宜的并行前向换掉昂贵的训练，总体划算。

**KL 怎么加**：GRPO 的 KL 约束不像 PPO 那样作为独立损失项，而是**直接做进奖励**（DeepSeek 实现）：

```
r_total = r_规则 − β·KL(π_θ || π_ref)     ← 每条回答的奖励扣掉 KL 惩罚，再组内归一化
```

KL 惩罚和奖励优化在同一套机制里完成，实现更简单。

#### 8.5.2 RLVR：Reinforcement Learning with Verifiable Rewards

**回答"奖励从哪来"**。传统 RLHF 的奖励来自 RM（人类偏好训练的打分器），三大毛病：**贵**（要收集人类排序、单独训练模型）、**有损近似**（可被 reward hacking 骗）、**标注不可规模化**（主观打分靠人工）。RLVR 对**能客观验证的任务**直接用"对错"当奖励，连 RM 都不需要：

- **数学**：最终答案与标准答案比对（数值/字符串相等）；
- **代码**：跑单测（编译 + 用例 assert 全过）；
- **格式规则**：是否按约定输出（如 `<think>` 标签内思考、最低长度）。

奖励要么 1、要么 0，**客观、零成本、机器自动生成**。

**为什么它是"推理模型火起来的前提"**（三点链）：

1. **可规模化**：数学题/代码题取之不尽，判据自动打分、无需人工标注 → RL 训练规模拉得起来；
2. **抗 reward hacking**：单测过了就是过了，没法用"看起来像推理的废话"骗分——必须真的算对、真的能运行；
3. **信号可信**：单测是 ground truth，模型收到的每个信号都干净（RM 是近似、可能错判）。

**例子**：prompt 让模型写"返回列表最大值的 Python 函数"，跑测试（含空列表、负数、重复元素）→ 全过给 1、任一失败给 0。模型被迫学会处理边界情况——**RL 直接把"工程严谨性"逼了出来**，纯 SFT 很难教。

**局限（面试加分点）**：

- 只适用**有客观判据**的任务（数学/代码/逻辑）；"写一篇好文章"这类主观任务仍要回 RM/人类偏好；
- **稀疏奖励**：G 条可能全军覆没，组内归一化后 advantage 全平、学不动 → R1 选任务要"有一定成功率但不饱和"；
- **过拟合判据表象**：可能学会"输出看似合理但没真推理"的文本碰运气。

#### 8.5.3 为什么 GRPO + RLVR 是绝配

| 需求                     | 谁解决                                    |
| ------------------------ | ----------------------------------------- |
| 省显存，才能把模型做大   | **GRPO**（省掉 critic）             |
| 大量可信奖励，才能训得动 | **RLVR**（规则/单测自动打分）       |
| 主观任务也要能训         | RLVR 之外保留 RM（R1 里有一个小 RM 兜底） |

**GRPO 的组内归一化恰好需要"同一 prompt 多条回答的分数"，而 RLVR 恰好能廉价地给 G 条回答全部打分（每条跑一遍规则/单测）**——两者在设计上天然咬合。没有 RLVR，GRPO 的 G 次采样打分成本太高；没有 GRPO，RLVR 驱动的 RL 会因 critic 显存开销难以扩大。

**DeepSeek-R1 的训练配方**（面试必背）：

```
1. 冷启动 SFT：几千条高质量长思考（CoT）种子样本，教模型"先想再答"的格式
   （没有这一步，RL 采样的答案格式太乱，奖励很难给）
2. 大规模 RL：数学/代码/逻辑任务，GRPO + 规则奖励 → 涌现自我纠错、反思（"aha moment"）
   （GRPO 省显存→能把模型做大；RLVR 提供可信奖励→能训得动）
3. 拒绝采样 + 全领域 SFT：用 RL 后的模型采样约 80 万条（60 万推理 + 20 万通用）做 SFT
   （把 RL 学到的东西"沉淀"固化下来，覆盖所有领域）
4. 第二轮 RL：对齐 + 无害性（加语言一致性奖励，防全英文/胡言乱语）
```

**蒸馏**：用 R1 生成的数据对 1.5B~70B 小模型做 SFT，小模型也能获得强推理能力（蒸馏比小模型自己 RL 便宜得多）。

**趋势判断**：RL 的角色从"对齐"升级为"能力发现"——o1/R1 证明 RL 能激发出训练数据里没有显式出现的推理行为（自我纠错、反思是 RL 在"单测必须过"的压力下**涌现**的）；配合 **test-time scaling**（RL 教会模型"想"，推理时给更多思考 token 决定"想多久"），成为推理模型的标准范式。

### 8.6 其他后训练技术一览

| 技术                          | 要点                                                                                               |
| ----------------------------- | -------------------------------------------------------------------------------------------------- |
| **拒绝采样微调（RFT）** | 从策略采样多个回答 → 筛选高奖励样本 → 做 SFT；简单有效的中间步骤                                 |

| **PRM（过程奖励模型）** | 给数学推理的**每一步**打分（对比 ORM 只给最终结果打分），缓解长推理的 credit assignment 问题 |
| **知识蒸馏**            | 大模型 logits / 生成数据 → 小模型                                                                 |
| **多轮对话 SFT**        | 用完整对话树训练，学会多轮状态管理与上下文利用                                                     |
| **工具 / Agent 强化**   | 用执行结果做奖励训练工具调用，见第九章                                                             |
| **模型合并（merging）** | 多个微调模型参数合并（算术平均、TIES），低成本组合能力                                             |

### 8.8 参数高效微调：LoRA 与 PEFT（面试高频）

**为什么需要 PEFT**：全量微调要更新所有参数——显存大、易灾难性遗忘、每任务存一版全模型。PEFT 只训练少量新增参数。

**LoRA 核心**：微调的权重更新是低秩的，拆成两个小矩阵：

```
W' = W + ΔW = W + B·A，  B∈R^{d×r}，A∈R^{r×k}，r << d
```

- 冻结原权重 W，只训 A、B（7B 模型可训练参数约 1%）
- 推理时把 B·A 合并回 W，**结构不变、零额外开销**
- 理论支撑：微调更新集中在低秩子空间（intrinsic dimension 低）

**关键超参**：

- r（秩）：越大越强但参数多，常用 8/16/64
- α（缩放）：增量权重 ×(α/r)，控制强度
- target modules：通常打在 Q、V 或所有线性层

**PEFT 全家桶对比**：

| 方法                 | 做法                  | 特点               |
| -------------------- | --------------------- | ------------------ |
| LoRA                 | 低秩矩阵近似 ΔW      | 推理零开销，最主流 |
| Adapter              | FFN 后插小 MLP        | 增加层深与延迟     |
| Prefix/Prompt Tuning | 加可学习前缀          | 不改权重，占上下文 |
| QLoRA                | 4-bit 量化基座 + LoRA | 单卡能微调 65B     |

**面试追问**：

- 为什么推理零开销？→ B·A 训练后合并回 W，模型结构不变
- 可训练参数怎么算？→ 每层 r×(d+k)，远小于 d×k
- LoRA 能注入新知识吗？→ 基本不能（同 SFT 限制），知识靠预训练/RAG
- LoRA 为什么有效？→ 微调 ΔW 天然低秩，低秩近似损失很小

**一句话**：LoRA 假设微调更新低秩，用两个小矩阵近似 ΔW，冻结基座只训增量——参数少、显存省、推理零开销。

### 8.9 模型量化（Quantization）

**为什么量化**：FP16 模型部署显存带宽压力大；量化到 INT8/INT4，显存减半以上、推理更快。

**量化级别**：

- W8A16 / W4A16：只量化权重，激活保高精度，最常用
- W8A8：权重+激活都量化，吞吐更高但精度损失大
- KV Cache 量化：缓存存 INT8，省显存（见 5.5）

**主流方法**：

| 方法                | 做法                               | 特点                    |
| ------------------- | ---------------------------------- | ----------------------- |
| PTQ（训练后量化）   | 校准数据估激活范围                 | 简单但精度损失大        |
| GPTQ                | 逐层最小化量化误差（Hessian 加权） | 精度接近 FP16，业界标准 |
| AWQ                 | 按激活重要性保护敏感通道           | 无需重训                |
| QAT（量化感知训练） | 训练时模拟量化误差                 | 精度最高但贵            |
| GGUF / llama.cpp    | 4-bit 格式                         | 消费级 CPU 能跑         |

**面试追问**：

- 为什么 INT8 还能保精度？→ scale+zero-point 仿射映射近似原分布，校准数据选好误差小
- 量化 vs 蒸馏？→ 量化压缩同一模型、蒸馏换成小模型，可组合
- QLoRA 是哪种？→ 4-bit 量化 + LoRA（见 8.8）

**一句话**：量化用低精度+缩放校准近似高精度权重，W4A16 是部署性价比最高的选择。

#### 8.9.1 模型剪枝（Pruning）

**定义**：移除模型中不重要的参数/结构，让模型变小。

| 类型                   | 做法                             | 特点                                     |
| ---------------------- | -------------------------------- | ---------------------------------------- |
| **非结构化剪枝** | 不重要的权重直接置零（稀疏矩阵） | 省显存，但稀疏矩阵硬件加速差             |
| **结构化剪枝**   | 删整行/整列/整个注意力头/整层    | 结构规整、能真实加速，性能掉了需微调恢复 |

**面试追问：LoRA / 量化 / 剪枝 / 蒸馏的区别（对象不同）**：

- **LoRA** = 训练方式（冻结原权重、只训低秩增量 ΔW=BA，不压缩模型）
- **量化** = 改数值精度（FP16→INT8/INT4，同一模型换表示）
- **剪枝** = 删结构（去掉不重要的参数/头/层）
- **蒸馏** = 学小模型（换一个更小的模型去模仿大模型）

> 记忆锚点：**LoRA 管"怎么训"，量化管"怎么存"，剪枝管"删什么"，蒸馏管"换小的"**。

#### 8.9.2 模型蒸馏（Distillation）

**定义**：用"大而强"的教师模型的知识训练一个小的学生模型，让学生逼近教师效果。

**核心机制——软标签（soft labels）**：

- 硬标签只告诉"这是猫"；教师输出的概率分布是**软标签**（80% 猫 / 15% 狗 / 5% 狐狸），**携带类间相似关系**（暗知识 dark knowledge），这是学生能学到东西的关键。
- **温度 T**：`softmax(z/T)`，T>1 使分布变平缓，把类间相似关系"摊开"暴露给学生。

**学生损失（双目标）**：`L = α·CE(学生, 软标签) + (1−α)·CE(学生, 硬标签)` —— 学教师的知识 + 学真实答案。

**大模型时代两种形态**：

- **黑盒蒸馏**：拿大模型输出当训练数据训练小模型（Alpaca/Vicuna 用 GPT-4 生成数据、DeepSeek-R1 用 R1 生成推理轨迹蒸馏到小模型）。成本低，是"小模型逼近大模型"的主要手段。
- **白盒蒸馏**：对齐教师/学生的中间层或注意力（DistilBERT、TinyBERT），信息更细但需访问教师内部。

**和量化/剪枝的区别**：蒸馏=**换成小模型**，量化=**改精度**，剪枝=**删结构**——方向不同、可组合。

> 面试一句话：蒸馏靠软标签把教师的"类间相似暗知识"传给学生，学生用 α 加权同时学软标签和硬标签；大模型时代主要是黑盒蒸馏（用大模型生成数据训小模型）。

## 九、工具调用（Tool Calling）训练 ★重点

### 9.1 问题定义：到底要训练什么

给模型一组工具（函数名 + JSON Schema 描述），模型要具备三个能力：

```
1. 格式（怎么调用）：输出符合约定的结构化调用 —— 函数名 + 合法参数
2. 时机（何时调用）：判断当前 query 是否需要外部信息/动作；需要则调用，不需要直接回答
3. 利用（调用之后）：把工具返回结果融入后续生成 —— 多轮调用、修正参数、失败重试
```

软件开发场景的典型工具：代码搜索/检索、读文件、编译、运行测试、静态分析、git 操作、依赖解析、API 调试、文档查询。

> 三个能力里，**格式靠 SFT 就能学会（数据问题），时机是真正的难点（决策问题），利用靠完整轨迹数据（环境问题）**。下面分别展开。

### 9.2 输出方式（怎么调用）：三大范式

**范式 A：JSON / JSON Schema（OpenAI、Gemini、DeepSeek 风格）**

工具定义通过 system 消息以 JSON Schema 传入：

```json
{
  "name": "run_tests",
  "description": "在仓库中运行 pytest 并返回测试结果",
  "parameters": {
    "type": "object",
    "properties": {
      "test_path": {"type": "string", "description": "测试文件路径"},
      "verbose":   {"type": "boolean", "default": false}
    },
    "required": ["test_path"]
  }
}
```

模型输出一个 JSON 对象：

```json
{"name": "run_tests", "arguments": {"test_path": "tests/test_utils.py"}}
```

- 训练要点：SFT 样本中把**工具定义放在上下文**、标签是 JSON 输出，让模型学会"按 schema 填参数"
- **工具描述（description）怎么写直接决定调用质量**——description 是模型选工具、填参数时唯一的语义依据，是训练数据构造中的人工投入重点

**范式 B：XML 标签（Claude 风格）**

```xml
<antml:function_calls>
  <antml:invoke name="run_tests">
    <antml:parameter name="test_path">tests/test_utils.py</antml:parameter>
  </antml:invoke>
</antml:function_calls>
```

- 优点：标签**成对出现、天然支持流式解析**（不用等 JSON 的右括号闭合就能边生成边解析）；多个 `<invoke>` 并列 = 并行调用
- 训练要点：模板 token 序列在数据中保持一致；混入"一次输出多个调用"的并行样本

**范式 C：特殊 token / DSL（Toolformer、DeepSeek 工具模式）**

- 词表里加专用 token（`<|tool_call|>`、`<|tool_response|>`），模型在"调用点"输出特殊 token 切换模式
- 或像 Toolformer 用可执行文本形式：`搜索("北京天气")`，训练时直接学习生成这种字符串
- 训练要点：**特殊 token 必须保留完整 token 边界**（不能被子词分词器切碎）；用特殊 token 分隔"调用 → 结果 → 继续生成"三段

**范式无关的统一要点（面试必答）：**

> "范式无关"指下面四点对 JSON/XML/特殊 token **三种格式都成立**——无论选哪种格式，这些训练规律不变。格式是"表"，范式无关要点是"里"。

1. **格式是"学"出来的**：构造"对话历史 → 工具调用 → 观察 → 回复"的完整轨迹样本，标准语言建模损失训练；loss 只算 assistant 部分
2. **训练管"会"，解码约束管"必对"**：推理时用 **constrained decoding**（grammar / JSON Schema 约束采样：Outlines、vLLM guided decoding、llama.cpp GBNF grammar、OpenAI structured outputs）保证输出 100% 格式合法——即使模型偶尔写错 JSON，解码层直接不允许非法 token
3. **工具定义与调用历史都要进上下文**：模型必须"看到"之前调用了什么、返回了什么，才能决定下一步
4. **必须混入通用数据**：工具样本占比过高（如 >30%）会导致模型"逢问题必调用"，形成 over-calling 的坏习惯

#### 9.2.1 格式是怎么"学"出来的

格式靠 **SFT（监督微调）** 学出来，机制就是最朴素的语言建模。构造样本时把工具调用作为目标输出拼在对话后面，用标准的下一个 token 预测损失训练，loss 只算 assistant 部分：

```
[对话历史 + 工具定义]
用户：仓库里 tests/test_utils.py 挂了，帮我修一下。
[系统] 可用工具：run_tests(test_path), read_file(path) ...

<assistant> 先跑一下测试确认错误信息。
{"name": "run_tests", "arguments": {"test_path": "tests/test_utils.py"}}   ← 目标输出，学这个
<observation> 2 failed: ...
<assistant> 错误集中在 utils 模块，定位源码。
{"name": "read_file", "arguments": {"path": "src/utils.py"}}              ← 继续学
```

模型学到的不是"格式规则"，而是 **token 序列的统计模式**：当上下文出现"可用工具"和"信息不足"时，下一个 token 应该是 `{`、`"`、`name`、`:`……经过上万条样本，格式的模式就被刻进参数里。

**为什么格式适合 SFT**：格式是**确定性的语法结构**——有明确的"标准答案"（合法的 JSON 就是合法的 JSON）。监督学习天生擅长学"给定输入、输出唯一正确答案"的东西，一次喂大量正确样例，样本效率极高。

**三层分工（面试必答框架）**：

```
SFT 学格式（"会"）     ← 格式的主要来源，监督学习灌进参数
RL  管时机/决策（"该不该调、调谁"）  ← 决策问题，见 9.3
constrained decoding 保格式（"必对"） ← 推理时兜底，保证 100% 合法
```

**为什么不用 RL 学格式**：RL 靠采样探索 + 奖励反馈，而合法 JSON 在所有可能的 token 序列里占比极其稀疏——让模型在几万个 token 的词典里瞎试、恰好凑出能解析的 JSON，概率极低，样本效率是灾难。SFT 直接喂正确样例一次就教会。**格式可以被 RL 当奖励用（校验），但不靠 RL 学**——比如 R1 的"格式规则奖励"（输出没按 `<think>` 格式就扣分）就是把格式合规当 RLVR 判据。

#### 9.2.2 Constrained Decoding 的工作机制

**核心思想**：在每一步解码时，根据"当前输出所处的语法状态"生成一个词表 mask，把会让输出变得非法的 token 的 logits 直接置 `-∞`，只在合法 token 里采样。因为每一步都保证"仍可到达合法终态"，最终序列**必然合法**。

```
正常：logits → softmax → 采样
约束：logits → mask（非法 token 置 -∞）→ softmax（只对合法 token）→ 采样
```

**具体例子（JSON 约束）**：约束"输出必须是含 name 和 arguments 的合法 JSON 对象"。

```
第 1 步：只有 { 能合法开启 JSON 对象 → }、"、run_tests 全部 mask → 采样出 {
第 2 步：处于"等待 key"状态 → 只有 " 合法 → 采样 "
第 3 步：处于"key 字符串内部" → name、test_path、run_tests 合法；{、: 非法
第 4 步：key 结束 → 只有 : 合法
……
```

每一步的"合法 token 集合"由当前语法状态决定，模型只负责在合法集合里选更合理的，合法性由解码器强制。

**三条实现路线**：

| 路线                          | 做法                                                                                                                         | 代表                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| **正则 → DFA**         | 正则编译成有限状态自动机，解码时维护"当前停在哪状态"，对每个候选 token 逐字符喂进自动机，任何一步无合法转移即非法            | Outlines、vLLM guided decoding      |
| **CFG 文法 → 解析器**  | 用 BNF 文法描述合法输出，编译成下推自动机（PDA）或 Earley 解析器，维护非终结符栈跟踪解析位置；表达力强于正则，能处理嵌套递归 | llama.cpp GBNF                      |
| **JSON Schema → 文法** | 把 JSON Schema 自动编译成"只生成符合该 Schema 的 JSON"的文法，再走路线 2                                                     | OpenAI structured outputs、Outlines |

**两个关键工程细节（面试加分）**：

1. **字符级 vs token 级对齐**：正则/文法工作在字符上，但解码是 token 级，一个 token 可能跨多个字符（如 `"test_path"` 是一个 token，含引号、字母、下划线）。实现要**把候选 token 逐字符喂进自动机**，检查整条路径是否合法——这是 constrained decoding 的主要计算开销。
2. **预计算 + 缓存**：自动机/文法每个约束只编译一次；常用技巧是**按自动机状态缓存"该状态下的合法 token 集合"**，避免每步重扫整个词表；还可用首字符粗筛先排除大量非法 token。

**和 logit bias 的区别**：

|      | **logit bias**（软约束） | **constrained decoding**（硬约束） |
| ---- | ------------------------------ | ---------------------------------------- |
| 做法 | 给某些 token 的 logits 加偏移  | 非法 token 的 logits 置`-∞`           |
| 保证 | 只是"倾向"，不保证合法         | **100% 保证**合法                  |
| 适用 | 引导风格、倾向                 | 必须格式合规的场景                       |

### 9.3 时机（何时调用）的训练：真正的难点

**为什么难**：调用还是不调用，没有唯一正确答案——这是**决策问题**，不是生成问题。模型容易走两个极端：

```
极端 1：从不调用 → 能力不足，回答依赖过时/缺失信息（幻觉）
极端 2：逢问必调 → 成本爆炸、响应慢、用户体验差（over-calling）
```

训练目标是让模型学会：**"当且仅当上下文中的信息不足以回答/完成任务时，才发起调用"。**

**第 1 层：SFT 数据设计（让模型"会区分"）**

- **混合两类样本**：
  - 需要调用的：实时信息（天气/股票）、仓库状态（代码在哪、测试挂了没）、外部动作（发邮件、跑构建）——答案依赖上下文之外的信息
  - 不需要调用的：常识、数学、闲聊——直接回答
- **负样本**：明确标注"直接回答"的样本；甚至构造"看起来要调用但其实不用调"的样本（比如用户问天气但系统已经把天气数据放进上下文了）
- **轨迹数据（trajectory）**：完整记录"思考 → 调用 → 观察 → 回答（或继续调用）"的轮次，由人工或教师模型**在真实环境中执行收集**（编译器、API 真跑）
- **执行反馈过滤**：对同一任务采样多条候选轨迹，**只保留真实执行成功的**（等价于拒绝采样——执行结果是天然的筛选信号）
- **课程式顺序**：先学"会调用"（早期数据全部带调用），再学"何时调用"（混合数据 + 决策负样本）

一个软件开发场景的完整轨迹样本（SFT 数据形态）：

```
用户：仓库里 tests/test_utils.py 挂了，帮我修一下。
[系统] 可用工具：search_code(关键词)、read_file(路径)、run_tests(路径)、edit_file(路径, 内容)

<assistant> 先跑一下测试确认错误信息。
<tool_call> run_tests(test_path="tests/test_utils.py")
<observation> 2 failed: test_parse_config, test_validate_path
<assistant> 错误集中在 utils 模块，先读源码定位。
<tool_call> read_file(path="src/utils.py")
<observation> <文件内容……>
<assistant> 定位到 parse_config 对空值处理有问题，修复它。
<tool_call> edit_file(path="src/utils.py", content="……")
<observation> 修改成功
<assistant> 已修复：问题是 parse_config 没有处理空值，现在补了默认值分支，测试应该能过了。
```

注意样本里**每一步"调用"都发生在信息不足的节点**——这就是"时机"在数据层面的体现。

**第 2 层：偏好与强化学习（让模型"学会决策"）**

- **奖励设计**（把"时机"变成可优化目标）：
  - 正确使用工具（该调时调、调对参数、用好结果）→ 正奖励
  - **不该调时调用（over-calling）→ 负奖励**（每次多余调用扣分 = 调用成本惩罚）
  - 该调不调、答错 → 负奖励
- **偏好对训练**：同一 query 构造"正确轨迹 vs 过度调用轨迹"、"正确轨迹 vs 漏调轨迹"，用 **DPO** 学决策（模型学会"调用与否"的偏好）
- **可验证奖励 RL（RLVR）**：用"最终答案通过测试/任务完成"做稀疏奖励（如 SWE-RL 用单测通过率训练代码智能体；Tulu 3 把工具使用纳入 RL 流水线）；工具执行结果可作为过程奖励
- **防 reward hacking**：模型可能学会"先随便调个工具再答"来刷分——必须把"调用必要性"纳入奖励，而不是只看"最终答对没有"

**第 3 层：推理时系统兜底（不训练也能部分解决）**

- **Router/意图分类器**：系统层先判断 query 是否走工具路径，把"何时调用"的决策从模型手里部分拿回来
- **Prompt 引导**："当且仅当信息不足时调用工具，否则直接回答"
- **失败重试策略**：调用失败（编译错误、404、超时）→ 把**错误信息拼回上下文**，让模型修正参数重试；重试必须**有依据**（根据错误信息调整），不能盲目重复——"失败 → 修正"的轨迹也要出现在训练数据里
- **成本控制**：调用次数上限、超时、并发限制

> **面试一句话总结"时间节点怎么训练"**：数据层面混入"需要调用/不需要调用"两类样本 + 负样本让模型会区分；优化层面用 DPO/RL 把"调用必要性"写进奖励，惩罚多余调用；系统层面用 router 和失败重试兜底。

### 9.4 训练数据从哪来（没有真实执行，就没有可靠的工具训练数据）

| 数据集/工作                             | 做法                                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Toolformer**                    | 自监督：让模型自己写 API 调用 → 真实执行 → 只保留"执行后困惑度下降"的样本（预训练阶段就学工具） |
| **Gorilla / APIBench**            | 从 API 文档自动生成 query-调用对，检索增强微调                                                    |
| **ToolLLM**                       | 16K 个真实 REST API + DFSDT（深度优先搜索决策树）采集高质量轨迹，用执行结果打分筛选               |
| **AgentLM / xLAM（AgentTuning）** | 跨多个开源数据集整理成统一轨迹格式，覆盖 ReAct 式多轮调用                                         |
| **自建流程（企业实践）**          | 种子工具集 → LLM 生成任务 → 真实环境执行验证 → 过滤失败轨迹 → 统一格式                        |

所有样本都要过**三重验证**：参数合法（schema 校验）、调用成功（真实执行）、结果被正确利用（观察出现在后续生成中）。

### 9.5 如何评估

| 层次     | 指标                                                                 | 说明                                                             |
| -------- | -------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 格式层   | JSON 可解析率、Schema 合规率                                         | 输出是否 100% 合法                                               |
| 单步能力 | 选对工具率、参数正确率                                               | BFCL（Berkeley Function Calling Leaderboard）用 AST/语义比较参数 |
| 决策质量 | **over-calling rate（多余调用率）**、漏调率、平均调用次数/成本 | 直接对应"时机"训练效果                                           |
| 任务层   | 多步任务完成率、真实环境成功率                                       | 代码场景即 SWE-bench 等 agent 评测                               |

**警惕 benchmark contamination**：公开的工具/代码评测集很容易混进预训练数据（题解、仓库、测试样例都在网上），评测前要自查去重，否则分数没有说服力。

### 9.6 从 Tool Calling 到 Agent

- **Tool calling = 单步能力**（会调用、调对参数）；**Agent = 闭环系统**（规划 + 记忆 + 反思 + 工具）
- 训练 Agent 的进阶路线：
  1. **能力 SFT**：ReAct 式轨迹（Thought → Action → Observation → …）作为序列样本，学会"会调用"
  2. **决策数据**：混合"需要/不需要调用"样本 + 负样本，学会"何时调用"
  3. **环境 RL**：对"最终任务完成"做强化（稀疏奖励 + 过程信号），学会"调出好结果"
- 评测从"单次调用对不对"升级为"整个任务能不能完成"

### 9.7 面试要点

| 考点                          | 答案要点                                                                                                                                                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 怎么训练模型学会输出格式      | SFT 数据混入工具调用轨迹（JSON/XML/特殊 token 任选其一并保持一致）+ 推理时 constrained decoding 兜底                                                                                                                     |
| 怎么训练"何时调用"            | 数据混合（需要/不需要调用的样本）+ 负样本 + 执行反馈过滤；DPO/RL 把"调用必要性"纳入奖励，惩罚 over-calling                                                                                                               |
| 调用失败怎么办                | 错误信息回填上下文 → 依据错误修正参数重试；"失败→修正"轨迹要出现在训练数据里                                                                                                                                           |
| 为什么必须混通用数据          | 防止 over-calling 和灾难性遗忘                                                                                                                                                                                           |
| 并行调用怎么学                | 轨迹样本中一个 assistant 轮次输出多个调用（XML 并列 invoke / JSON 数组）                                                                                                                                                 |
| 工具 description 重要吗       | 非常重要：它是模型选工具、填参数的唯一语义依据                                                                                                                                                                           |
| 结构化输出如何保证 100% 合法  | 训练 + constrained decoding（grammar/JSON Schema 约束）双保险                                                                                                                                                            |
| constrained decoding 怎么实现 | 每步按当前语法状态 mask 非法 token（logits 置 -∞）只在合法集合采样；三条路线：正则→DFA（Outlines/vLLM）、CFG 文法→PDA（GBNF）、JSON Schema→文法（OpenAI）；关键是字符/token 对齐逐字符检查 + 按状态缓存合法 token 集 |
| 数据为什么必须真实执行        | 没有执行验证就无法过滤"参数看似合法但调用失败"的坏样本                                                                                                                                                                   |

## 十、RAG（检索增强生成）

### 10.1 核心概念

**R**etrieval-**A**ugmented **G**eneration

**不让 LLM 全靠记忆回答问题，而是让它先"查资料"再回答。**

LLM 的知识截止于训练数据，且容易产生幻觉。RAG 在推理时实时检索外部知识库，把检索结果作为上下文拼进 prompt，让模型基于可靠来源生成回答。

### 10.2 工作流程

```
                              ┌──────────────────┐
用户问题                      │   文档/知识库      │
    │                         │  （PDF、网页、笔记） │
    ▼                         └────────┬─────────┘
┌──────────┐                           │
│  Query   │ ← 可能重写/扩展查询         ▼
│  处理    │               ┌─────────────────────┐
└────┬─────┘               │  文档切块（Chunking） │
     │                     │  每个块 → Embedding  │
     ▼                     │  存入向量数据库       │
┌──────────┐               └──────────┬──────────┘
│  向量检索 │ ←──── 语义相似度 ────────┘
│ (向量DB) │   检索 top-k 最相关的文档块
└────┬─────┘
     │
     ▼
┌──────────────┐
│ Prompt 组装   │  「参考以下资料回答问题：{检索结果}\n\n问题：{用户问题}」
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  LLM 生成    │  基于检索到的上下文生成回答（含引用来源）
└──────────────┘
```

### 10.3 关键组件

| 组件                           | 作用                           | 常用选型                                 |
| ------------------------------ | ------------------------------ | ---------------------------------------- |
| **文档切块（Chunking）** | 把长文档切成小块，每块独立检索 | 固定大小（256/512 tokens）+ 重叠窗口     |
| **Embedding 模型**       | 将文本块和查询转成向量         | text-embedding-3, BGE, Jina              |
| **向量数据库**           | 存储向量 + 做相似度搜索        | Milvus, Pinecone, Chroma, Weaviate       |
| **检索策略**             | 如何从库中找到最相关的块       | 语义检索, 关键词 BM25, 混合检索 + 重排序 |
| **LLM**                  | 根据检索上下文生成回答         | GPT-4, Claude, LLaMA 等                  |

> **混合检索补注（Hybrid Retrieval，面试常问）**
>
> 两条互补路线**同时跑、再融合结果**：
>
> - **稀疏检索（BM25 / TF-IDF）**：精确词匹配，擅长专有名词、代码、ID、缩写；盲区是"同义改写"（"车"↔"汽车"匹配不上）
> - **稠密检索（向量语义）**：embedding 余弦相似度，擅长近义词与改写；盲区是精确字符串、稀有术语可能被向量糊掉
>
> 融合方式：
>
> - **加权分数融合**：`score = α·BM25 + (1−α)·向量分`（需先各自归一化）
> - **RRF（Reciprocal Rank Fusion）**：按排名位置融合 `Σ 1/(k+rank)`，不用调分数尺度，更鲁棒
>
> 完整链路：**双路召回 top-100 → 交叉编码器（Cross-Encoder）重排 → 取 top-5 → 进 LLM**。粗召回保广度、精排保精度。

### 10.4 为什么需要 RAG

| 问题                   | RAG 如何解决                               |
| ---------------------- | ------------------------------------------ |
| **幻觉**         | 强制基于外部事实来源生成，而非纯记忆       |
| **知识过时**     | 知识库可随时更新，无需重训模型             |
| **领域知识不足** | 专业文档即时注入，弥补通用预训练的知识空白 |
| **可追溯性**     | 回答可附引用来源，用户可验证               |
| **成本**         | 避免为新增知识频繁微调大模型               |

### 10.5 RAG vs 微调

|                    | RAG                                      | 微调                   |
| ------------------ | ---------------------------------------- | ---------------------- |
| **知识更新** | 改文档即可，实时生效                     | 需要重新训练           |
| **成本**     | 低（只需维护向量库）                     | 高（需要 GPU 训练）    |
| **适用场景** | 事实性问答、知识密集型任务               | 改变模型行为风格、格式 |
| **上限**     | 受检索质量限制                           | 受训练数据规模限制     |
| **组合使用** | 可以同时做：微调改"风格"，RAG 提供"事实" |                        |

### 10.6 高级 RAG 优化

| 技术                      | 说明                                                                    |
| ------------------------- | ----------------------------------------------------------------------- |
| **Query Rewriting** | 检索前用 LLM 重写用户问题，弥补用户表述与文档表述的差距                 |
| **HyDE**            | 先让 LLM 生成一个假设性答案，用这个答案做检索（文档更接近答案而非问题） |
| **Re-ranking**      | 粗检索 top-100 → 精排模型（Cross-Encoder）重排 → 取 top-5             |
| **Self-RAG**        | LLM 自己判断是否需要检索、检索结果是否有用、生成的回答是否可靠          |
| **Graph RAG**       | 知识图谱 + 向量检索，实体关系可以补全向量检索遗漏的关联信息             |

### 10.7 GraphRAG：知识图谱增强检索

**核心问题：普通 RAG 的"见树不见林"。** 普通 RAG 按片段相似度检索，只适合"某个片段里就有答案"的**局部事实型**问题；但对**答案分散在跨多篇文档、需要全局归纳或关系推理**的问题（"整份语料主要讲了哪几个主题""这几个概念之间什么关系"），没有任何单个片段和问题足够相似，向量检索天然无能为力。GraphRAG 正是为这类问题设计的。

**两步管线（微软 2024，From Local to Global）：**

```
① 离线索引
   语料 → LLM 抽取实体 + 关系 → 构建知识图谱
        → 社区检测（Leiden 算法）把图切成社区
        → 对每层社区用 LLM 生成摘要 → 得到"从粗到细的分层社区摘要"
           （相当于把整篇语料压缩成结构化的全局视角）

② 查询
   全局性问题（Global Search）→ map-reduce：
      挑出与问题相关的社区摘要 → 各自生成局部答案 → 合并成最终答案
   实体级问题（Local Search）→ 取该实体的邻域 + 相关文本单元 + 社区摘要
```

**和普通 RAG 的对比：**

| 维度     | 普通 RAG                   | GraphRAG                              |
| -------- | -------------------------- | ------------------------------------- |
| 检索粒度 | 片段级（chunk 相似度）     | 结构级（实体/关系 + 社区摘要）        |
| 擅长     | 局部事实型问题             | 跨文档、关系型、全局归纳问题          |
| 实现     | 向量检索 + 重排            | LLM 建图 + 社区检测 + 摘要 + map-reduce |
| 成本     | 低（只需维护向量库）       | 高（索引要大量 LLM 调用）             |
| 查询延迟 | 低                         | 全局查询多轮 LLM 调用，较高           |

**代价与局限（面试别只说优点）：**
- **索引贵**：每个 chunk 要 LLM 抽实体/关系、每个社区要 LLM 写摘要，语料大时成本可观；
- **延迟高**：全局查询的 map-reduce 要多轮 LLM 调用；
- **依赖抽取质量**：实体/关系抽歪了，图就带偏；
- **实践用混合**：局部事实问题走向量检索，跨文档关系型问题走 GraphRAG。

> **面试一句话**：GraphRAG = 用 LLM 把语料构造成知识图谱 + 社区检测生成分层社区摘要，查询时 map-reduce 综合，解决普通 RAG 答不了"跨实体、跨文档"全局问题；代价是索引贵、全局查询慢，实践中和向量检索按问题类型混合用。

### 10.8 面试要点

| 考点               | 答案要点                                                                              |
| ------------------ | ------------------------------------------------------------------------------------- |
| RAG 解决的核心问题 | 幻觉和知识更新，让模型回答基于外部来源以缓解幻觉                                      |
| Embedding 检索原理 | 将查询和文档块用 Embedding 模型映射到同一向量空间，计算余弦相似度以找语义最相近的内容 |
| Chunk Size 的权衡  | 太小→丢失上下文，太大→检索精度下降，通常 256-512 tokens + 重叠                      |
| RAG 的瓶颈在哪     | 检索质量决定生成质量上限，"垃圾进垃圾出"                                              |
| 幻觉怎么系统缓解   | RAG + 引用来源 + 约束解码 + 高质量 SFT/RL 拒绝；根因是模型"不知为知"                  |
| 长文档怎么切块     | 按段落/标题语义切块 + 重叠窗口 + 递归拆分，避免切断语义                               |
| 混合检索怎么做     | 稀疏 BM25 + 稠密向量双路召回 → 交叉编码器重排 → 融合取 top-k                        |
| GraphRAG 解决什么问题 | 普通 RAG"见树不见林"，答不了跨文档/关系型/全局归纳问题；答案分散在多个片段、没有单片段足够相似 |
| GraphRAG 怎么实现     | 两步：LLM 抽实体关系建知识图谱 → 社区检测(Leiden)+ 分层社区摘要 → 查询时 map-reduce 综合 |
| 和普通 RAG 区别       | 片段级 vs 结构级；局部事实 vs 全局关系；代价：索引贵、全局查询慢 |
| GraphRAG 的局限       | 索引贵(大量 LLM 调用)、全局查询延迟高、依赖实体抽取质量；实践按问题类型混合用 |

## 十一、LLM Agent（智能体）

### 11.1 核心概念

Agent（智能体）= **LLM + 工具使用 + 规划能力 + 记忆系统**，让模型不仅能"说"，还能"做"。

```
┌───────────────────────────────────────────┐
│                  Agent                     │
│  ┌─────────────┐    ┌──────────────────┐  │
│  │   LLM 大脑   │───▶│  思考 + 决策     │  │
│  └──────┬──────┘    └────────┬─────────┘  │
│         │                    │             │
│         ▼                    ▼             │
│  ┌─────────┐         ┌──────────┐         │
│  │  记忆    │         │  工具调用  │         │
│  │ 短期+长期│         │ 搜索、代码、  │         │
│  └─────────┘         │ API、文件等  │         │
│                      └──────────┘         │
│                           │                │
│                           ▼                │
│                      ┌──────────┐         │
│                      │  外部环境  │         │
│                      │ 返回结果   │         │
│                      └─────┬────┘         │
│                            │               │
│                            ▼               │
│                   观察结果 → 反思 → 再行动   │
└───────────────────────────────────────────┘
```

### 11.2 Agent 的四个核心模块

| 模块                       | 作用                        | 实现方式                                   |
| -------------------------- | --------------------------- | ------------------------------------------ |
| **LLM（大脑）**      | 推理、规划、决策            | GPT-4, Claude, LLaMA 等                    |
| **工具（Tools）**    | 执行 LLM 无法独自完成的操作 | 搜索 API、代码执行器、数据库查询、文件操作 |
| **记忆（Memory）**   | 跨对话轮次保持上下文        | 短期：对话历史；长期：向量数据库存储       |
| **规划（Planning）** | 把复杂任务分解为子步骤      | ReAct, Plan-and-Execute, Tree of Thought   |

### 11.3 ReAct 模式（核心推理框架）

**Re**asoning + **Act**ing：思考和行动交替进行。

```
Thought: 用户想知道北京今天天气。我需要先查天气 API。
Action: search_weather("北京")
Observation: 北京今天晴，22-30°C
Thought: 我已获得天气信息，可以回答用户了。
Answer: 北京今天晴，气温 22 到 30 度……
```

### 11.4 主要 Agent 框架

| 框架                        | 特点                                                          |
| --------------------------- | ------------------------------------------------------------- |
| **ReAct**             | 思考-行动-观察循环，最基础的 Agent 范式                       |
| **Plan-and-Execute**  | 先整体规划再分步执行                                          |
| **AutoGPT / BabyAGI** | 自主设定子目标并循环执行                                      |
| **Multi-Agent**       | 多个 Agent 分工协作（如 AutoGen, CrewAI）                     |
| **Function Calling**  | LLM 输出结构化函数调用，而非自由文本——最工业化的 Agent 形态 |

### 11.5 Function Calling 流程

```
用户："帮我给张三发一封邮件，主题是明天的会议，内容提醒他带报告"

LLM 输出（结构化）：
{
  "function": "send_email",
  "parameters": {
    "to": "张三",
    "subject": "明天的会议",
    "body": "张三，提醒你明天的会议请记得带上报告。谢谢！"
  }
}
       ↓
代码执行 send_email() → 返回结果 → LLM 告知用户"已发送"
```

工具定义需要给 LLM 提供 JSON Schema，描述函数名、参数类型、参数含义。

> 上面的例子是"系统提示 + 推理时约定"的应用层用法。**模型本身如何被训练出"会输出这种结构化调用、知道什么时候该调用"**，是第九章"工具调用训练"的内容——训练好的模型调用更可靠、更少幻觉。

### 11.7 Agent 的分类与认知架构（CoALA）

面试时把 Agent 讲得"系统化"，推荐用 **CoALA**（Cognitive Architectures for Language Agents）的框架：任何 Agent = **记忆 + 行动空间 + 决策循环** 三件套。

```
记忆（Memory）
 ├─ 工作记忆：上下文窗口（当前 prompt + 历史）
 ├─ 情景记忆：过去任务的经历（episode 记录）
 └─ 语义记忆：长期事实知识（向量库 / 知识库）
行动空间（Action Space）
 ├─ 内部推理：思考、规划、反思（不接触外部世界）
 ├─ 外部检索：查文档、查数据库、RAG
 └─ 外部工具：API 调用、代码执行、浏览器、操作系统
决策（Decision-Making）
 ├─ 规划：把目标分解为子任务（Plan-and-Execute）
 └─ 反思：根据结果修正策略（Reflexion）
```

**两种常见分类维度**（面试可答"Agent 有哪些类型"）：

| 维度         | 分类                       | 例子                                                         |
| ------------ | -------------------------- | ------------------------------------------------------------ |
| 按决策方式   | 单次调用 / 循环式 / 搜索式 | LLM API 一次生成 / ReAct 循环 / ToT、LATS 树搜索             |
| 按学习方式   | 上下文内学习 / 微调学习    | Prompt 即兴 Agent / AgentTuning、RL 训练的 Agent（见 11.11） |
| 按智能体数量 | 单 Agent / 多 Agent        | 单个 ReAct / MetaGPT、AutoGen（见 11.10）                    |

核心观点：**Agent 是"LLM + 记忆 + 行动空间 + 决策循环"的复合系统，每个组件都可以独立设计**——这也是"Agent 研究"能脱离 LLM 本身单独成为一个方向的原因。

### 11.8 推理增强范式：搜索、反思、规划

| 范式                     | 论文/代表                          | 思想                                             | 解决的问题                                   |
| ------------------------ | ---------------------------------- | ------------------------------------------------ | -------------------------------------------- |
| **树搜索**         | ToT（Tree of Thoughts）            | 把思维链展开成树，用评估器打分 + 搜索（BFS/DFS） | 单条 CoT 容易走偏，需要"多条路径 + 回溯"     |
| **蒙特卡洛树搜索** | LATS（Language Agent Tree Search） | MCTS + ReAct + 反思，把搜索用到"行动"上          | 行动空间也值得搜索：试错 + 反馈              |
| **语言反思**       | Reflexion                          | 环境反馈 → 自然语言反思 → 写进记忆 → 下次更好 | 不更新参数也能从错误中学习（"语言强化学习"） |
| **自我修正**       | Self-Refine                        | 生成 → 自我反馈 → 修正，循环                   | 首轮输出质量不够，靠自评迭代                 |
| **先规划后执行**   | Plan-and-Execute                   | 先产出整体计划，再逐步执行                       | ReAct 边想边做容易短视，先规划减少中途改道   |

面试要点：这些方法的共同本质是**用"算力/多轮"换"质量"**——搜索是空间换质量、反思是反馈换质量、规划是结构换质量。面试被问"Agent 怎么变强"，先答这四条线，再补一句"2025 年的答案是直接训练"（见 11.11）。

### 11.9 记忆系统：从上下文窗口到分层记忆

- **Generative Agents（Smallville 小镇，UIST 2023）**：25 个模拟人的经典记忆架构
  ```
  记忆流（Memory Stream）：记录所有经历（带时间戳 + 重要性分）
      ↓ 定期
  反思（Reflection）：聚合相关记忆，提炼高层抽象结论
      ↓ 决策时
  规划（Planning）：根据记忆与反思递归分解行动计划
  ```
- **MemGPT / Letta（ICLR 2024）**：把**操作系统分页思想**搬给 LLM——
  - 工作记忆 = 上下文窗口（容量小、贵）
  - 外部记忆 = 磁盘（向量库，容量大）
  - LLM 自己"分页"：上下文快满时把不重要的内容"换出"到外部存储，需要时再"换入"
  - 解决了"长对话 / 长文档超出上下文窗口"的问题
- **RAG vs 记忆的区别**（面试常问）：
  - RAG = 查询**外部知识库**（知识不是模型的经历）
  - 记忆 = 存储**自身经历**（做过什么、用户偏好、上一步结果）
  - 工程上长期记忆常落地为：向量库 + 检索 + 写入时机管理

面试一句话：**"上下文窗口不是记忆"**——窗口只是工作记忆，真正的长期记忆需要分层存储 + 检索 + 遗忘策略。

### 11.10 多智能体协作（Multi-Agent）

| 代表                           | 协作方式                                                                                          | 特点                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| **MetaGPT**（ICLR 2024） | **SOP 流水线**：产品经理→架构师→工程师→QA，通过结构化产物（PRD、设计文档、代码）逐级传递 | 像软件公司：用"文档接口"代替口头交流，减少歧义 |
| **ChatDev**              | 瀑布流角色扮演：CEO/CTO/程序员/测试员用自然语言"开会"讨论                                         | 全过程对话，产出完整软件项目                   |
| **AutoGen**（微软）      | 对话式编排：可配置多个 conversable agents 互相发消息                                              | 灵活、可人机混合、支持工具                     |
| **AgentVerse**           | 多角色协商 + 评价                                                                                 | 观察多 agent 社会行为                          |

- **收益**：角色分工（每 agent 专注一个子任务）、并行、角色约束减少单 agent 的"幻觉漂移"
- **代价**：token 成本成倍增长、协调开销、**错误在多 agent 间放大传播**
- 面试要点：多 agent **不是越多越好**；两类协作设计——"结构化产物传递"（MetaGPT，接口清晰）vs "自由对话协商"（ChatDev/AutoGen，灵活但不可控）

> **四个框架详细展开（面试背诵版）**：
>
> - **MetaGPT（ICLR 2024）——"文档接口派"**：解决多 agent 对话信息丢失/发散。核心创新 = **SOP 标准化作业流程**（产品经理写 PRD → 架构师画系统设计 → 工程师写代码 → QA 测试），agent 之间靠**共享消息池 + 发布-订阅**传递**结构化产物**（PRD/设计/代码），不靠聊天——"文档是唯一事实来源"，接口清晰可控。
> - **ChatDev——"角色扮演派"**：瀑布流阶段（设计→编码→测试），每阶段两个角色（如 CEO+CTO、CTO+程序员）**自然语言"开会"讨论**，产出阶段性文件。与 MetaGPT 对比：**MetaGPT 是"产物的传递"，ChatDev 是"过程的对话"**。
> - **AutoGen（微软）——"框架派"**：不预设流程，提供 **ConversableAgent** 积木（能收发消息的 agent + UserProxyAgent 代表人类 + GroupChat 群聊编排）。特点：**灵活自定义拓扑、可人机混合（human-in-the-loop）、支持工具调用**。代表"自由对话协商"设计——灵活但不可控。
> - **AgentVerse——"社会派"**：强调**协商 + 评价机制**（发言 → 协商 → 投票/评价裁决），用来**观察多 agent 的社会行为**（观点如何形成、如何达成共识），关心协作过程本身而非单纯产出。
>
> **面试速查**：协作媒介（文档/对话/消息/协商）、流程（预设 SOP/瀑布/自由编排/协商）、可控性（MetaGPT 高、ChatDev 中、AutoGen 低但灵活、AgentVerse 中）、人机介入（仅 AutoGen 强）。**收益** = 分工 + 并行 + 角色约束减幻觉漂移；**代价** = token 成倍 + 协调开销 + 错误放大传播。两类设计：**结构化产物传递 vs 自由对话协商**。

### 11.11 Agent 的训练路线（2024-2025 前沿，重点）

核心观点：**Agent 能力是"训练"出来的，不只是"提示"出来的**——2024 年后业界从"prompt 编排 Agent"转向"训练出 Agent 能力"。

```
路线 1：数据合成（AgentInstruct，微软 2024）
  用 seed 任务 + 纠错循环 + 工具真实执行，自动合成 10 万级高质量
  （指令遵循、工具调用、纠错）训练数据 → 开源模型效果逼近 GPT-4 级 agent 能力

路线 2：统一轨迹微调（AgentTuning / xLAM / AgentOhana）
  AgentTuning（ICLR 2024）：把 6 个开源 agent 数据集统一成 ReAct 轨迹格式微调，
    模型泛化到未见过的环境
  xLAM（Salesforce，2024）：把函数调用/工具轨迹数据规模化，训练"大动作模型"

路线 3：强化学习训练（Agentic RL，2025 主流）
  SWE-RL（2025）：代码仓库 + 单测通过 = 可验证奖励，稀疏奖励下模型涌现
    "自己跑测试验证、根据报错修改"的多轮行为
  Agent-R1（2025）：把 R1 式 RL 搬到工具使用，训练"何时调用工具"的决策
  Kimi K2（Moonshot，2025）：1 万亿参数大规模 agentic RL，证明 RL 路线可以规模化
```

> **"统一轨迹微调"的本质与局限（面试追问）**：
>
> 机制上就是 **SFT + 交叉熵**：把 ReAct 轨迹当 token 序列做下一个 token 预测，loss 只算 assistant/action 部分——本质是**行为克隆/模仿学习**，能同时学到调用格式和"上下文→行动"的决策模式。
>
> 局限（为什么还要 RL）：**没有 credit assignment**（只学"当时做了什么"，不学"为什么好"）、**无探索**（只复制看过的轨迹）、**错误累积**（多步任务一步错步步错，推理时自生成状态偏离训练分布）。所以统一轨迹 SFT 是 RL 之前的廉价基础，真正的决策优化靠 agentic RL（路线 3）。

**训练三要素**（面试总结用）：

1. **数据**：真实执行反馈（ToolLLM）、合成数据（AgentInstruct）、统一轨迹（AgentTuning）
2. **目标**：格式（结构化调用）+ 决策（何时调用，见第九章）
3. **奖励**：可验证奖励（单测/答案）+ 执行结果 + 调用成本惩罚

对比"提示工程 Agent"：提示编排（ReAct prompt）开箱即用但不可靠；训练后的 Agent（xLAM、Kimi K2）调用更准、决策更稳、幻觉更少——这是 Agent 工程化的分水岭。

### 11.12 代码与工具 Agent 的前沿形态

**（1）ACI：接口设计决定 Agent 上限（SWE-agent, NeurIPS 2024）**

SWE-agent 提出 **Agent-Computer Interface（ACI）**：给代码 agent 设计的不是通用终端，而是专门工具集（查看文件、定向搜索、编辑 + lint 反馈），成功率大幅提升。

> 面试金句：**工具的"接口设计"本身就是研究点**——Agent 的输入输出格式（观察空间 + 动作空间）设计得越好，模型越容易用对。类似观点延伸到 MCP（见下）。

**（2）评测闭环：SWE-bench / SWE-bench Verified**

- SWE-bench：2294 个真实 GitHub issue→PR 任务，要求模型在真实仓库中定位、修改、通过测试
- SWE-bench Verified：OpenAI 与普林斯顿合作的精选子集，成为代码 agent 事实标准
- 教训：`pass@1` 只看第一次答案是否碰巧对，**无法反映 agent 利用反馈迭代的能力**；评测必须"执行验证"而不是文本匹配

**（3）产品形态**：Devin（Cognition）、Claude Code（Anthropic）、OpenAI Codex、开源 OpenHands——agentic coding 成为 2025 年最热的软件工程产品形态

**（4）工具接入标准化：MCP（Model Context Protocol）**

Anthropic 2024 年底发布的**模型上下文协议**：统一"工具/数据源 ↔ LLM"的接入标准（类似 USB-C），一次接入到处可用，已成为事实标准。面试可答：MCP = 工具生态的标准化接口层，解决"每个 agent 都要重新适配工具"的碎片化问题。

**（5）Computer Use（计算机使用）**

- 行动空间从"调用 API"扩展到"操作真实 GUI"：观察（截图）+ 动作（点击、输入、滚动）
- 评测：OSWorld（NeurIPS 2024，真实桌面操作系统 369 个任务）
- 代表：Claude computer use（2024）、OpenAI Operator（2025）
- 趋势：**行动空间越接近人类操作，agent 能做的事越广**，但可靠性、安全、成本挑战更大

**（6）Deep Research（深度研究 agent）**

OpenAI Deep Research / Gemini：把"搜索 → 阅读 → 综合 → 引用"组织成多轮长流程，产出研究报告——浏览器成为 agent 的主要工具之一。

### 11.13 评测体系与开放问题

**评测分层**（面试可画这条线）：

```
单步：BFCL（函数调用：选对工具、参数正确）
多轮：τ-bench（含"用户模型"，测"该不该调用工具、怎么与用户交互"）
任务：AgentBench（8 个环境）、GAIA（通用助手）、SWE-bench（代码）
环境：WebArena / Mind2Web（网页）、OSWorld（操作系统）、MLE-bench（ML 工程）
```

**评测陷阱**：

- **Benchmark Contamination**：公开仓库、题解、测试样例容易混进预训练数据，分数虚高
- **pass@1 局限**：不反映迭代/反馈利用能力，agent 评测要看"多轮任务完成率"
- **文本匹配 vs 执行验证**：必须真实执行（编译、测试、API 调用）才算数

**开放问题**（面试"难点"题素材）：

1. **长任务错误累积**：一步错步步错，且难以回溯定位（credit assignment）
2. **安全**：prompt injection（工具返回内容里藏指令劫持模型）、tool poisoning（恶意工具）、权限与沙箱、多 agent 间信息泄露
3. **成本与延迟**：一次任务几十次 LLM 调用，token 成本与响应延迟是商业化瓶颈
4. **记忆与状态管理**：长会话的状态一致性、遗忘与更新
5. **评测自动化**：用 agent 评 agent，评测本身也可能被污染

### 11.14 Agent 的 Skill（技能）与技能库

**核心概念**：Skill = 可复用的**程序性知识**——把"怎么完成任务"的步骤沉淀成可执行、可检索、可组合的单元，让 Agent 不必每次从零规划。

**为什么需要**：Agent 每次任务都从头推理很浪费；人类会"熟能生巧"。把成功经验沉淀成 skill，下次类似任务直接复用 → **越用越强（终身学习）**。

**代表工作：Voyager（Minecraft，2023）** 引入 **Skill Library（技能库）**：

```
1. 写（Write）：每完成一个子任务，把解法写成一段可执行代码（函数）作为 skill
2. 验证（Verify）：代码在环境中真实执行成功才入库（执行反馈 = 质量门槛）
3. 存（Store）：按功能描述存入技能库，用向量检索索引
4. 用（Retrieve/Compose）：新任务检索最相关 skill，组合出解决方案
```

**Skill vs 记忆（面试常问）**：

- 记忆 = **陈述性知识**（知道什么：事实、经历）
- Skill = **程序性知识**（知道怎么做：行动流程）
- 类比：记忆是"昨天吃过这家店"，skill 是"怎么骑车"——后者是刻进流程的能力

**Skill vs 工具（Tools）**：

- 工具 = 外部提供的功能（read_file、search），Agent 调用
- Skill = Agent 自己从经验里长出来的能力（把多次工具调用组合成一段可复用流程）

**Skill vs 统一轨迹 SFT（11.11）**：

- SFT = 把外部轨迹**灌进参数**（隐式技能，改权重）
- 技能库 = 把经验**存在外部可检索代码**（显式技能，不改权重）
- 互补：一个改模型能力、一个当外挂知识；2025 年业界把 skill 做成产品级可复用组件（如 OpenAI Skills）。

**面试答法**：

> Agent 的 Skill 是可复用的程序性知识——把成功的执行步骤沉淀成可执行、可检索、可组合的单元，让 Agent 终身学习、越用越强。代表作是 Voyager 的技能库：Agent 每完成一个子任务就把解法写成代码，在环境里真实执行成功才入库，新任务时检索最相关的技能组合复用。它和记忆的区别是程序性 vs 陈述性——记忆是"知道什么"，技能是"知道怎么做"；和工具的区别是工具由外部提供、技能由 Agent 自己沉淀。它也和统一轨迹 SFT 互补：SFT 把轨迹灌进参数，技能库把经验存在外部。

## 十二、多模态（Multi-Modal）

### 12.1 核心概念

多模态指模型能同时理解和处理文本、图像、音频、视频等多种输入形式，在它们之间建立关联。

人类的认知是多模态的——看到一个苹果、听到"苹果"这个词、闻到苹果的香味，大脑把三者对齐。多模态 AI 追求的就是这种跨通道理解。

### 12.2 核心思路

**把所有模态"翻译"到文本空间**，因为文本是 LLM 的"母语"：

```
图像 ──CLIP ViT──→ 图像 token ──┐
音频 ──Whisper───→ 音频 token ──┼──→ LLM（统一处理）──→ 文本输出
视频 ──每帧编码──→ 视频 token ──┘
```

### 12.3 主流方案：Visual Encoder + 投影 + LLM

```
图像 → 切成 patch（小块）→ CLIP ViT 编码 → 每块一个向量
      → 投影层（MLP）→ 映射到 LLM 的 token 空间
      → 生成的"视觉 token"拼在文本 token 前面
      → LLM 统一处理 → 生成文本回复
```

代码逻辑：

```python
image_tokens = vision_encoder(image)    # CLIP → [N, 1024]
image_embeds = projector(image_tokens)  # MLP  → [N, 4096]（与 LLM 同维度）
input_embeds = concat([image_embeds, text_embeds])
response = llm(input_embeds)
```

这个方案的优点：**不用改 LLM 的架构**，Transformer 天然能处理"前面是图后面是文字"的混合序列。

### 12.4 典型模型

| 模型                      | 模态           | 方案                                  |
| ------------------------- | -------------- | ------------------------------------- |
| **CLIP** (OpenAI)   | 图文匹配       | 双编码器（文本 + 图像），对比学习对齐 |
| **LLaVA**           | 图文理解       | CLIP ViT + MLP 投影 + LLaMA           |
| **GPT-4o**          | 文、图、音     | 原生多模态（细节未公开）              |
| **Gemini** (Google) | 文、图、音、视 | 原生多模态                            |
| **DALL-E 3**        | 文→图         | CLIP 理解文字 → 扩散模型生成图像     |
| **Sora** (OpenAI)   | 文→视频       | 扩散 Transformer（DiT）               |
| **Whisper**         | 音→文         | Encoder-Decoder，语音识别             |

### 12.4.1 CLIP 详解（OpenAI 2021 · 图文对比对齐的奠基工作）

**一句话**:CLIP 用**图文对比学习**,把图像和文本映射到**同一个语义向量空间**——"配对的图文要接近,不配对的要远离"。它是"对比学习能学出可迁移跨模态表示"的标志性证明。

**架构(双塔 + 对比)**
```
图像 → 图像编码器(ResNet 或 ViT) → 图像向量 z_I
文本 → 文本编码器(Transformer)  → 文本向量 z_T
两者投影到同一 d 维空间,算余弦相似度 → 拉近匹配对、推远不匹配对
```

**训练(InfoNCE 对比损失)**
- batch 内 N 个图文对,构造 N×N 相似度矩阵:对角线是正样本对(配对的图文),其余 N²−N 个是负样本对
- 对每个图文对做"在 batch 里找出自己的配对"——本质是 N 路分类,softmax + 交叉熵,带温度 τ
- **batch 必须大**(CLIP 用 32768):负样本越多,对比信号越强、表示越好

**怎么用:zero-shot 分类(不用训练分类头)**
- 把每个类别名写成一段文本("a photo of a cat"),文本编码器算文本向量
- 图像编码器算图像向量,与所有类别文本向量算余弦相似度,取最大的那个类别 = 预测结果

**和你的面试衔接(钩子句式 4/5 的支撑)**
- CLIP 是**图文对**上的对比学习;稠密检索是 **query-文档对**上的对比学习——同一套 InfoNCE,只是配对的"对"不同
- 多模态的"对齐枢纽":LLaVA 等把 CLIP ViT 当**视觉编码器**,视觉 token 由 CLIP 产出再喂给 LLM
- 你在推荐里做的 item-GCL、在 Harness 里做的检索,和 CLIP 是同一个思想家族:"拉近相关的、推远不相关的",所以你说"对比学习在大模型时代还有用"完全站得住

**缺点(面试被追问时)**
- **固定分辨率**:输入图被缩放到固定尺寸,细节丢失
- **细粒度/属性/计数/空间关系弱**:分不清"两个苹果"还是"三个苹果"、难答"球在桌子上面还是下面"
- **数据偏置**:训练数据是网上抓的图文对,有噪声和文化/性别偏置

**面试速答**
> CLIP 用图文对比学习把图像和文本映射到同一向量空间——batch 内配对的图文拉近、不配对的推远(InfoNCE,大 batch + 温度 τ)。它能零样本分类:把类别写成文本、和图像算余弦相似度取最大。它是多模态的"对齐枢纽",LLaVA 就用它做视觉编码器;和稠密检索是同一套对比学习,只是配对的"对"从图文换成了 query-文档。缺点是对细粒度、计数、空间关系理解弱,而且有数据偏置。

### 12.5 面试要点

| 考点                     | 答案要点                                                                                                               |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 多模态怎么"对齐"         | 对比学习（CLIP 拉近匹配图文、拉远不匹配图文），把不同模态映射到同一语义空间                                            |
| 为什么文本是"母语"       | 文本数据量最大、结构最丰富，LLM 在文本上能力最强，其他模态"翻译"成文本 token 复用 LLM 的推理能力                       |
| 挑战                     | 各模态数据规模不均（文本 >> 图像 >> 视频）、时序对齐（视频帧与字幕）、跨模态幻觉                                       |
| 跨模态幻觉怎么缓解       | 更充分的图文对齐预训练、解码约束、多模态评测修正（如 POPE）                                                            |
| 视频理解怎么做           | 抽帧 + 音频特征压缩为时序 token；长视频需要记忆/检索架构                                                               |
| 为什么不直接训原生多模态 | 多模态数据远少于文本，先复用文本能力，文本作为对齐枢纽                                                                 |
| CLIP 怎么训练            | 图文对比学习（InfoNCE）：匹配图文对拉近、不匹配对拉远；双塔编码 + 余弦相似度                                           |
| 图像怎么变成 token       | ViT 把图像切 patch 嵌入；或视觉编码器输出再过投影层（LLaVA 用 MLP）映射到 LLM 空间                                     |
| 视觉 token 太多怎么压缩  | Q-Former / Perceiver：用少量 query 从视觉特征中抽取信息（BLIP-2 把 256 patch 压成 32 token）                           |
| 对齐架构三种方案         | ①early fusion 视觉 token 直接拼进文本（LLaVA）②cross-attention 每层插入视觉（Flamingo）③Q-Former 压缩再进（BLIP-2） |
| 多模态怎么评测           | 图文检索 recall@k / VQA / MMBench / MMMU；幻觉用 POPE、CHAIR                                                           |
| CLIP 的缺点              | 固定分辨率；细粒度、属性、计数、空间关系理解弱；有训练数据偏置                                                         |
| CLIP 在多模态里的角色 | 对齐枢纽:图文映射到同一语义空间;LLaVA 等用它做视觉编码器喂给 LLM |
| CLIP 和稠密检索的关系 | 同一套对比学习(InfoNCE):CLIP=图文对、稠密检索=query-文档对;都拉近正对、推远负对 |
| 为什么视频比图像难       | 帧多冗余大、时序依赖、逐帧 token 爆炸；需抽帧压缩 + 时序建模 + 记忆/检索                                               |

## 十三、总结对比表

### 架构演化

```
2017 Transformer ──→ 2018 BERT (Encoder-only, 理解)
         │           2018 GPT  (Decoder-only, 生成) → GPT-2 → GPT-3 → GPT-4
         │
         └──→ 2019 T5/BART (Encoder-Decoder, Seq2Seq)

位置编码演进：正弦/可学习绝对编码 → 相对编码（T5/ALiBi）→ RoPE（LLaMA/Qwen/DeepSeek，主流）

训练流水线演进：预训练 → SFT → RLHF(PPO) → +DPO → +GRPO/RLVR（R1 推理路线）→ +工具调用特化

Agent 演进：ReAct（思考+行动）→ 多智能体框架（AutoGen/MetaGPT）→ 工具调用训练（xLAM/AgentTuning）→ agentic RL（SWE-RL/Kimi K2）→ 产品化（Claude Code/Operator）
```

### 现代 LLM 完整训练流水线（速记）

```
预训练（知识，第七章）→ SFT（格式与行为，第八章）→ 偏好对齐 RLHF/DPO/GRPO（第八章）
→ 能力特化（工具调用 / 长上下文 / 推理，第九、六章）
→ 推理时：RAG / 约束解码 / test-time scaling
```

### 核心能力对比

|                    | BERT           | GPT/LLM        | RAG            | Agent          | 多模态         |
| ------------------ | -------------- | -------------- | -------------- | -------------- | -------------- |
| **能做什么** | 读懂文本       | 生成文本       | 基于资料回答   | 自主完成任务   | 理解图像/音频  |
| **注意力**   | 双向           | 单向因果       | 无（组合方案） | 无（组合方案） | 同 LLM         |
| **输出**     | 标签/span      | 自由文本       | 带引用的文本   | 工具调用+文本  | 文本（或图像） |
| **部署成本** | 低（CPU 能跑） | 高（多卡 GPU） | 中（需向量库） | 高（多次调用） | 高（多编码器） |

### 技术选型指南

| 场景                          | 推荐方案                                              |
| ----------------------------- | ----------------------------------------------------- |
| 固定任务、数据充足、成本敏感  | 微调 BERT                                             |
| 通用对话、内容生成            | GPT/Claude/LLaMA 等 LLM                               |
| 知识库问答、企业文档          | RAG + LLM                                             |

## 十四、前沿模型独特机制与行业影响（面试加分项）

### 14.2 DeepSeek 引爆复盘：机制如何变成行业影响（核心）

面试被问"DeepSeek 为什么能引爆？"，用**四层拆解**讲，每层都有记忆点：

**第一层：技术杠杆——每个机制解决一个硬约束**

| 机制                 | 解决什么                    | 量化效果                        |
| -------------------- | --------------------------- | ------------------------------- |
| MLA                  | KV Cache 显存/带宽瓶颈      | Cache 减 ~93%，长上下文不炸显存 |
| 细粒度 + 共享 MoE    | 参数量 vs 单 token 算力矛盾 | 总参 671B / 每 token 只激活 37B |
| FP8 混合精度         | 训练吞吐                    | 相比 BF16 约翻倍                |
| MTP（多 token 预测） | 训练信号偏"水"              | 每个位置多预测，信号更密        |
| DualPipe 双向流水线  | 流水线气泡浪费              | 前向/反向与通信重叠，气泡近零   |

五个机制合力 → **同质量下训练成本降一个数量级**。注意：这是组合式创新，不是单点突破——单看每个都不算新（MoE 有 Switch Transformer，FP8 有前人的低精度训练），**把它们在一个系统里咬合起来**才是 DeepSeek 的贡献。

**第二层：成本数字——把技术优势翻译成可传播的数字**

- 14.8T tokens / 278.8 万 H800 GPU 小时 / 按 $2/h 算约 **$5.6M**
- 对比：Llama 3 405B（稠密）约 3084 万 GPU 小时 → 便宜约 **11 倍**
- 数字为什么有传播力：它击碎了一个普遍假设——"前沿模型训练费要上亿美元"。现在五百万美元就能做，**门槛假设被改写**。

**第三层：市场与叙事——为什么在 2025 年 1 月引爆**

- R1 于 2025-01-20 发布，**开源权重 + 免费 App** 让普通用户第一次亲身体验"会思考"的 AI，App 冲上美区下载榜第一；
- 2025-01-27 英伟达单日 **-17%**，市值蒸发约 $589B（当时美股史上单日最大市值蒸发）；
- 双重冲击：**能力**（推理接近 o1）+ **价格**（开源免费）同时落地；
- 地缘叙事：在算力出口管制下逼近前沿 → 打破"算力决定论"；
- 时机：正值 AI 资本开支泡沫争论最热、市场处于高位。

**第四层：范式转移——什么被永久改变**

1. **训练成本预期被重置**：小预算 + 开源也能逼近前沿，"效率竞赛"取代"堆算力竞赛"；
2. **开源权重成为常态竞争力**：闭源模型不再自动等于"更好"；
3. **RL 的角色从"对齐"升级为"能力发现"**（o1/R1 之后）——RL 能激发出训练数据里没有显式出现的能力；
4. **架构方向被改写**：MLA/MoE/稀疏注意力/低精度训练成为新标配的探索方向。

> **面试金句**：DeepSeek 是"架构（MoE+MLA）+ 精度（FP8）+ 系统（DualPipe）+ 目标（MTP）"的组合式创新，它们共同压低训练成本；而"引爆"是成本数字、开源推理能力、地缘叙事、市场时点四者共振的结果——技术是必要前提，但不是充分原因。

### 14.3 前面章节没覆盖的前沿机制细节

**（1）Multi-Token Prediction（MTP）——多 token 预测**

标准 LM 每个位置只预测下一个 token，且相邻 token 往往很好猜（"信号偏水"）。MTP 让每个位置**并行预测未来 k 个 token**（多个预测头）：

- DeepSeek-V3 用 1 个额外预测头；Meta（Eureka lab，2024）证明多 token 预测在**代码**任务上样本效率显著提升
- 好处：训练信号更密、能学到更长程的结构（如括号匹配、函数签名→函数体）
- 附带收益：预测头可复用做**投机解码**的草稿模型
- 代价：参数增加、训练吞吐略降

**（2）DeepSeek Sparse Attention（DSA）——分层稀疏注意力**

MoE + MLA 之后，注意力本身的 FLOPs 和缓存成为长上下文的下一瓶颈。DSA 的思路是**不平均用力**：

- **底层用全注意力**：保留全局信息，负责理解整个序列
- **高层按 token 类型用稀疏注意力**：指令/文档/历史对话分别只关注各自需要的部分（配 LightSeer 做 KV 压缩）
- 效果：推理时注意力 FLOPs 大幅下降，支撑更长上下文（DeepSeek-V3.1/V3.2 使用；同门还有 NSA 原生稀疏注意力论文）

**（3）FP8 混合精度训练**

- 用 E4M3/E5M2 两种 FP8 格式（前向/反向用不同尾数位），DeepSeek-V3 是首个大规模 FP8 训练的模型
- 相比 BF16 吞吐约翻倍；难点是量化误差累积——需要 block-wise 缩放、主权重保持 FP32
- 意义：证明"低精度不是玩具"，工业级训练可以全程 FP8

**（4）DualPipe——双向流水线并行**

传统流水线并行把模型按层切分跨卡串行，卡间有"气泡"（前向等反向的空闲）。DualPipe 用**双向调度 + 计算与通信重叠**，气泡接近零——这是把训练吞吐再往上顶的工程创新。

**（5）test-time scaling（o1 路线）**

- 推理时生成更多"思考 token"换取准确率，与训练时的 RL 互补：**RL 教会模型"想"，test-time 决定"想多久"**
- 配套工程：把思考 token 的算力成本纳入部署规划（"slow thinking" 贵但准）

**（6）MoE 的通信优化**

- MoE 的 token 路由是 all-to-all 通信，是跨节点瓶颈（H800 互联带宽还被砍半）
- 对策：node-limited routing（限制 token 最多跨几个节点）、分组路由、DeepSeek 的补丁策略——这也是为什么 DeepSeek 的 MoE 在"残血硬件"上仍能高效
